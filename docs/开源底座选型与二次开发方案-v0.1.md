# 开源底座选型与二次开发方案 v0.1

> 日期：2026-09-19 ｜ 状态：**待你确认底座选择**
> 前序文档：`docs/财报核验Agent-方案设计-v0.1.md`（总体设计）
> 本文件回答两个问题：**(一) 这算不算 Agent 项目？(二) 从哪个开源项目上二次开发？**

---

## 一、先纠正上一轮的表述偏差

上一轮我写的是「**不引入 Agent 框架**」，理由是分支只有 2–3 个。这不是「不做成 Agent」——是两个不同的概念。Agent 与否取决于**谁在决定下一步**，不取决于你用不用框架。

不过你既然要投 Agent 岗，我重新权衡后**改口**：**上一轮的建议对你不合适，本轮修正。**

### 1.1 修正后的建议

| | 上一轮 | 本轮（修正） |
|---|---|---|
| 编排层 | 手写状态机 | **改用显式图框架**（Pydantic AI 的 `pydantic_graph`），把 agent loop 画出来 |
| 工具调用 | 写死调用顺序 | **LLM 经 function calling 自主选择工具**，自己决定调哪个、调几次 |
| 理由 | 分支少，写死更简单 | 你要投 Agent 岗，"循环与分支可见"比"代码少 100 行"更值钱 |

### 1.2 我实测过了，这条路走得通

今天实测你给的这个通道（`glm-5.3`），三项能力全部可用：

| 能力 | 实测结果 |
|---|---|
| 工具调用（function calling） | ✅ 模型正确选择 `search_annual_report`，参数 `{"metric":"营业收入","period":"2023-12-31"}` |
| 结构化输出（`json_schema` 严格模式） | ✅ 六元组 7 个字段一个不少，返回合法 JSON |
| span 原文命中 | ✅ 模型回吐的 `source_span` 与原文逐字一致 |

所以「LLM 自主选工具」不是纸上设计，是已验证可行的。

### 1.3 面试官认「Agent」的五条判据（可检验）

一个项目要满足以下条件，才会被认作 Agent 而不是「套了 LLM 的脚本」：

| # | 判据 | 我们的落法 | 证据形态 |
|---|---|---|---|
| 1 | **≥2 个工具由 LLM 经 function calling 自主选择** | 挂 6 个工具（见 4.2），不写死调用顺序 | 执行轨迹日志里能看到模型请求了哪个工具 |
| 2 | **下一步由工具返回决定**（条件边），非预设顺序 | 证据不足 → 改写查询重试；六元组缺字段 → 拒答 | 图的边是条件边，可画出来 |
| 3 | **有预算上限，Agent 自主决定终止** | `max_steps` / 时间 / 成本三重预算，超限优雅终止 | 预算超限率作为评测指标单独报 |
| 4 | **工具观察回灌下一轮上下文**（perceive→reason 闭环） | 检索结果进下一轮 messages | messages 轨迹可导出 |
| 5 | **拒答是状态机的可达状态**，不是模型自由发挥 | 六元组缺字段 → 程序级拒答分支 | 拒答率单独报 |

我们这套「六元组 + Decimal + 程序级拒答」的设计，**天然满足全部五条**——因为 Agent 想给出答案，就必须先检索、再校验六元组、不足则拒答。这比一个"能聊天"的 Agent demo 更能证明 Agent 能力。

## 二、候选全景（三层，别混为一谈）

很多人把这三个层次的东西放在一起比，那是比不出结论的。

| 层 | 是什么 | 候选 |
|---|---|---|
| **应用平台层** | 能直接跑起来的完整 RAG/Agent 应用 | RAGFlow、Dify、FastGPT、MaxKB、AnythingLLM、kotaemon、QAnything、Open WebUI |
| **框架层** | 提供编排运行时，你写业务 | LangGraph、Pydantic AI、OpenAI Agents SDK、Microsoft Agent Framework、CrewAI、agentUniverse |
| **底座层** | 解析、索引、定位、评测的具体能力 | MinerU 4.0、RAG-Anything、Docling、RAGAS、ALCE |

## 三、应用平台层打分（含 RAGFlow 为什么不合适）

权重：引用可溯源 25% / 改造成本 20% / 单进程 15% / 协议友好 15% / 社区活跃 15% / 代码可读 10%。
（理由：六元组与页码定位是判分点，权重最高；二次开发要求你改得动、讲得清。）

| 项目 | 协议 | 引用粒度 | 单进程 | 加权分 |
|---|---|---|---|---|
| **kotaemon** | Apache-2.0 | **页码级 + 高亮** | ✅ pip 可直接跑 | **4.85** |
| Open WebUI | BSD-3 + 强制品牌条款 + CLA | chunk 级 | ✅ | 3.80 |
| AnythingLLM | MIT | chunk/源级 | 桌面单二进制 | 3.65 |
| **RAGFlow** | Apache-2.0 | **页码 + bbox** | ❌ 需 5 个容器 | 3.50 |
| MaxKB | 开源（LICENSE 条款未核实） | chunk 级 | 单容器 | 3.30 |
| Dify | 改版 Apache-2.0（禁多租户 SaaS、禁去 Logo） | 文档级 | ❌ | 2.70 |
| QAnything | **AGPL-3.0**（强 copyleft） | 源级 | ❌ | 2.70 |
| Verba | BSD-3 | chunk 级 | ✅ | 2.70（**已归档废弃**） |
| FastGPT | 改版 Apache-2.0 | chunk 级 | ❌ | 2.30 |

### ⛔ RAGFlow 不适合做整体二次开发，四个具体原因

1. **部署形态不匹配**：需要 `docker compose` 起 **5 个容器**（Elasticsearch + MySQL + Redis + MinIO + 应用），内存 8–16GB。你的约束是"单进程起步、不上微服务"，这一条就冲突。
2. **改造成本高**：代码是 **C++ / Go / Python 混合**，深度文档解析（DeepDoc）核心在 C++，你要改"检索粒度"和"证据结构"得动核心，不是加插件。
3. **面试风险**：面试官必问"你的检索是怎么实现的"——如果答案是"RAGFlow 内部做的"，后面的追问（分块策略是什么？rerank 用的什么？bbox 从哪来？拒答在哪触发？）会全部答不上。**校招看的是"你做了什么"，不是"你用了什么"。**
4. **它的优点你只需要一半**：RAGFlow 真正强的是 DeepDoc 表格解析（页码 + bbox），但解析这一层你已经定了 MinerU，**不需要为了拿一个解析能力背上五个容器**。

> **RAGFlow 的正确用法**：如果你的 MinerU 方案全部失败，**单独起它的 DeepDoc 解析服务**作为降级路径，而不是整体 fork。

## 四、推荐方案：分层取用，不做整体 fork

### 4.1 一句话结论

**二次开发的对象是「MinerU 4.0 + Pydantic AI 的图」，核心核验层自建；不 fork 任何大而全平台。**

### 4.2 完整选型清单

| 层 | 选型 | 协议 | 是"二次开发"还是"直接依赖" |
|---|---|---|---|
| PDF 解析 | **MinerU 4.0**（standard 档，Apple Silicon） | MinerU Open Source License（Apache 2.0 + 附加条款，落地前核 `LICENSE.md`） | 直接依赖 |
| 索引 + 定位 | **MinerU 4.0 doclib**（SQLite + FTS5 + 稳定 locator） | 同上 | 直接依赖，**这是省下最多工作的一块** |
| 检索 | 轻量混合：FTS5(jieba) + 本地向量 + RRF | 自建 | **自建** |
| Agent 编排 | **Pydantic AI**（`pydantic_graph` 显式图） | MIT | **二次开发** |
| 工具契约 | Pydantic schema（`@agent.tool`） | — | 自建 |
| **六元组 + span 硬校验** | **自建** | — | **自建，核心贡献** |
| **Decimal 计算 + 公式注册表** | **自建** | — | **自建，核心贡献** |
| **程序级拒答** | **自建** | — | **自建，核心贡献** |
| 离线质量门 | **RAGAS**（faithfulness / context recall）+ **ALCE**（citation recall/precision） | Apache-2.0 / MIT | 直接依赖 |
| 前端 | CLI + **PyMuPDF 渲高亮 PNG** | — | 自建 |

### 4.3 为什么这样分

**核心判断：MinerU 4.0 已经把你最重的一块工作做完了，而它做完的那块恰好不是面试考点。**

MinerU 4.0 自带 **doclib**（本地文档库：FastAPI 守护进程 + SQLite + FTS5 全文检索），并提供**稳定定位符**：

```
doc:{文档id}/tier:{档位}/page:{页码}/block:{块号}
doc:{文档id}/tier:{档位}/page:{页码}/block:{块号}/char:{字符偏移}
```

页码与块号都是 **1-based**，且官方明确要求「不得剥离 locator 字段，续读与引用都需要它」。

这直接解决了本项目"证据要能回指页码"的底层问题——**你不用自己从 `content_list` 反推页码映射了**。省下来的时间全部投到面试真正会问的三件事上：六元组、span 校验、Decimal 计算。

反过来说，如果 fork RAGFlow，你花一周时间在跟容器和 C++ 编译较劲，最后能讲的还是"我配了个工作流"。

### 4.4 关键问题：span 校验要不要用现成库？

**自己写。** 我查过了：

- 业界**没有**"对 PDF 原文片段做字符串级校验"的现成库。
- RAGAS 的 `faithfulness` 是**离线评估指标**（把答案拆 claim + NLI 判断），不是运行时校验，也不做 span 匹配。
- ALCE 提供 citation 质量评估（citation recall/precision），同样是**离线指标**。
- RARR / SELF-RAG 要么围绕 web search 设计，要么需要微调模型，对本项目过重。

所以分工是：**运行时校验自己写（约 50–100 行，归一化 + 子串匹配 + 坐标反查，零依赖、完全可控）；离线质量门复用 RAGAS / ALCE。**

## 五、Agent 工具集设计（6 个工具，LLM 自主选择）

这是"真 Agent"的具体落点——**不写死调用顺序**，由模型决定。

| 工具 | 用途 | 输入 schema | 输出 | 错误码 |
|---|---|---|---|---|
| `search_evidence` | 混合检索年报证据 | `{metric, period, top_k}` | 候选证据列表（带页码/片段） | `NO_RESULT` |
| `locate_table_row` | 在财务报表页精确定位表格行 | `{statement, metric, period}` | 行值 + 行列坐标 | `TABLE_NOT_FOUND` |
| `verify_identity` | 勾稽核验（走 Decimal） | `{formula_id, operands}` | `PASS / WARN / FAIL` + 差额 | `MISSING_OPERAND` |
| `convert_unit` | 单位换算（万元 ⇄ 元） | `{value, from_unit, to_unit}` | 换算后 Decimal | `UNIT_UNKNOWN` |
| `fx_rate` | 汇率查询（读本地汇率表） | `{from_ccy, to_ccy, date}` | 汇率 Decimal | `RATE_NOT_FOUND` |
| `list_periods` | 探查文档覆盖哪些报告期 | `{}` | 期间列表 | `NO_DOC` |

**LLM 的自主空间**：决定先检索还是先探期间、决定换关键词重试、决定调不调 `verify_identity`、决定够不够回答还是拒答。

## 六、明确不推荐的清单（附理由，避免你重复调研）

| 项目 | 为什么不选 |
|---|---|
| **FinGPT** | 它是**模型微调项目**，不是 Agent，方向完全不同 |
| **FinRobot** | 基于 LangChain 的模板堆叠，偏"生成研报"，与"证据溯源 QA"距离远；且整体是完整产品，难局部剪裁 |
| **OpenBB** | 实时行情/宏观数据平台，你明确说了不做实时行情；且依赖云服务，本地单进程跑不起来 |
| **TradingAgents** | 多 Agent 交易辩论，场景完全不同（且它本身是 LangGraph 写的完整 App） |
| **KAG**（蚂蚁） | 需要自建 SPG 知识图谱 + Java/Go 服务，重；且引用只到 chunk 级，不满足"页码 + 原文片段"；最后发版 2025-06，已停滞约一年 |
| **Dify / FastGPT** | 协议是改版 Apache-2.0（禁多租户 SaaS、禁去 Logo），且是应用平台不是底座 |
| **QAnything** | AGPL-3.0 强 copyleft，会传染你的整个仓库 |
| **Verba** | **已归档废弃**，不要用 |
| **CrewAI** | 角色扮演式编排，结构化输出弱，难证明"LLM 自选工具"，面试容易讲成黑盒 |

### 关于 agentUniverse（蚂蚁）的单独说明

调研里它被推为"金融垂直首选"（Apache-2.0、有 OpenTelemetry 可观测、源自蚂蚁金融实践）。**我判断它不适合你**，理由：

- 它是**多 Agent 协作框架**（PEER / DOE 模式），而你自己的开发要求文档里明确写了「多 Agent 只有职责隔离、可并行子任务或独立校验产生可测收益时再引入」。你的场景是单报告核验，单 Agent 足够。
- 体量约 2.3k star、版本 v0.0.19（**0.0.x 版本号**），工程成熟度对校招项目是风险。
- 引入它你会花时间在"理解蚂蚁的编排范式"上，而不是在"把六元组和 Decimal 做扎实"上。

**它值得借鉴的是可观测性设计（OpenTelemetry 埋点导出每步耗时/工具/token），这部分我们自建即可，不需要引入框架。**

## 七、备选方案：如果你坚持要 fork 一个完整应用

如果你觉得"从零长出来的代码库"不够像"项目"，或者简历上需要一个具体的开源项目名，那么：

**唯一值得 fork 的是 kotaemon**（Apache-2.0、约 25k star、Python + Gradio、**引用可到页码级并支持 PDF 内高亮**、`pip` 可单进程跑）。

改造清单（一周）：

1. 读 `libs/ktem/ktem/reasoning/`，摸清它的 retrieve → generate 管线
2. 写自定义 reasoning 模块，强制 chunk 元数据含六元组字段，缺字段即拒答
3. 抽出计算层：建 Decimal 工具节点，操作数只取检索值
4. 复用它的 PDF.js 高亮引用组件，把六元组页码接上去
5. 加程序级 validator 判证据充足性
6. 接 FinanceBench + 消融实验

**代价**：你会继承一个 Gradio 聊天应用的架构，而我们的核心是一条核验流水线。多出来的部分（会话管理、多用户、模型切换 UI）对你的考点评分没有帮助，反而增加面试时被问倒的面。

**我的判断**：kotaemon 的价值在于**它的引用高亮 UI 组件**。如果你后面要做 Web 演示，抠这个组件（或直接用 PyMuPDF 渲高亮 PNG）就够了，不必 fork 整个应用。

## 八、结论

| 问题 | 答案 |
|---|---|
| 这是 Agent 项目吗？ | **是**，且修正了编排层选型后更"Agent"：LLM 经 function calling 自主选 6 个工具、条件边决定重试或拒答、预算上限内自主终止 |
| 从哪个开源项目二次开发？ | **MinerU 4.0**（解析 + 索引 + 定位，直接依赖其 doclib 与 locator）+ **Pydantic AI**（编排层，二次开发图结构） |
| 核心层谁写？ | 六元组、span 硬校验、Decimal 计算、程序级拒答 —— **全部自建，这是你的原创贡献** |
| RAGFlow 用不用？ | **不整体用**。仅当 MinerU 全部失败时，单独起它的 DeepDoc 解析服务作为降级路径 |
| 需要提前准备什么？ | 无。凭证已配好并实测通过 |
