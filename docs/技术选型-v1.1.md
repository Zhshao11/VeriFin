## 二、选型的输入约束

选型不是选"最先进的"，是选"满足约束的"。本项目有 7 条硬约束：

| # | 约束 | 来源 | 对选型的影响 |
|---|---|---|---|
| 1 | 技术栈只锁 Python + LLM | 你的要求 | 排除 C++/Go 为主的项目（如 RAGFlow 的 DeepDoc 核心） |
| 2 | **每个数字必须可追溯到页码 + 原文片段** | 核心需求 | 解析器必须输出页级定位信息，这是第一权重 |
| 3 | **缺证据必须拒答，不允许编造** | 核心需求 | 需要程序级护栏，不能依赖提示词 |
| 4 | 所有算术走 Decimal | 精度要求 | 需要一个模型无法绕过的计算层 |
| 5 | 单进程、本地跑、不上微服务 | 你的要求 | 排除需要多容器编排的方案 |
| 6 | 1 周出 MVP | 你的要求 | 排除学习曲线陡、需自建知识图谱的方案 |
| 7 | 要投 Agent 岗，循环与分支需可讲解 | 你的要求 | 编排层需要显式图，不能是黑盒（见 §3.4） |

## 三、逐层选型

### 3.1 PDF 解析

**选型：MinerU 4.0（主解析） + PyMuPDF（定位层与兜底）**

#### 候选打分

权重：表格能力 25% + 页码可定位 25% + 跨页处理 15% + 中文支持 15% + 部署成本 10% + 稳定性 10%。
权重理由：约束 #2（页码溯源）与财务表格识别是本项目的判分点，故表格与页码各占最高权重。

| 候选 | 表格 | 页码定位 | 跨页 | 中文 | 部署 | 稳定 | 加权 |
|---|---|---|---|---|---|---|---|
| **MinerU 4.0** | 5 | 4 | 3 | 5 | 3 | 3 | **4.05** |
| PP-StructureV3 | 5 | 4 | 3 | 5 | 2 | 3 | 3.95 |
| Docling | 4 | 4 | 3 | 3 | 5 | 4 | 3.80 |
| PyMuPDF / 4LLM | 3 | **5** | 2 | 3 | 5 | 5 | 3.75 |
| pdfplumber | 2 | **5** | 1 | 3 | 5 | 5 | 3.35 |
| Marker | 3 | 2 | 2 | 3 | 3 | 3 | 2.60 |
| Unstructured | 2 | 3 | 2 | 2 | 2 | 3 | 2.35 |

#### 选 MinerU 的理由

1. **它原生输出稳定 locator**，形如 `doc:{文档id}/tier:{档位}/page:{页码}/block:{块号}`，页码与块号均为 1-based。官方明确要求"不得剥离 locator 字段，续读与引用都需要它"。这直接满足约束 #2，**省掉自己从解析结果反推页码映射的工作**。
2. **自带本地文档库 doclib**，底层是 SQLite。已实测确认其数据落在 `/Users/shihao/.mineru/doclib.db`。
3. 中文表格识别在公开横评（OmniDocBench）中处于第一梯队，且是免费开源方案里少数同时满足"表格强 + 中文强 + 带页码"的选择。

#### 为什么还要加 PyMuPDF

**因为 MinerU 的定位信息不足以单独完成溯源：**

- MinerU 输出的是归一化坐标（0–1000），**不能直接在 PDF 上画框**做高亮。
- 跨页表格默认只保留首页的页码，页码连续性会断。
- PyMuPDF 提供**绝对坐标 + 精确页码**，正好补上这两点，且在 MinerU 单页解析失败时可以兜底。

两者是互补而非冗余：**MinerU 负责"读懂"，PyMuPDF 负责"指得准"。**

#### ⚠️ 已实测的三个 MinerU 使用门槛（不查会浪费时间）

| 现象 | 根因 | 处理 |
|---|---|---|
| `mineru parse` 报 `server_not_running` | 4.0 的解析走本地服务 | 先 `mineru server start` |
| 报 `Local parse-server is disabled` | 配置项 `parse_server.local.mode` 默认为 **`disabled`** | 需显式 `mineru config set parse_server.local.mode managed` |
| `--pages` 不传时只解析**前 10 页** | 默认值是前 10 页，不是全部 | 整份年报必须显式传 `--pages all` |

另外模型不会随 pip 安装自动下载，需执行：

```bash
.venv/bin/mineru-kit models download --tier standard   # 约 2GB
```

#### ✅ 实测结论：中文财报解析质量（2026-09-19 实跑）

**测试样本**：贵州茅台 2024 年年度报告（3.5 MB / 143 页），取合并报表段 `--pages 58-67`、`--tier standard`。
**产物**：`data/parsed/moutai2024_fs`（218 行 / 32 KB）。

| 观测项 | 实测结果 | 结论 |
|---|---|---|
| 页码切分 | 10 页正文产出 10 个 `<!-- page N of 143 -->` 标记 | ✅ 可程序化稳定切页 |
| 数字保真 | `59,295,822,956.89`、`298,944,579,918.70` 原样输出，未丢位、未四舍五入 | ✅ 满足"数字不得被改写"的硬要求 |
| 表格结构 | `<table><tbody><tr><td>` 完整保留，`colspan` 保留，空单元格保留为空 `<td>` | ✅ 可还原行列 |
| 披露单位 | 表头 `单位:元 币种:人民币` 被原样解析出来 | ✅ 容差推导所需的单位可直接取到 |
| 数值可解析率 | 356 行中 178 行的"本期"列可解析为数值（其余为表头、分区标题、空行） | ✅ 无脏数据 |
| **会计恒等式** | `资产总计 298,944,579,918.70 = 负债合计 56,933,264,798.10 + 所有者权益合计 242,011,315,120.60`，差额 **0.00**，容差 ±1.5 元 → **PASS**（本期/上期两列均 PASS） | ✅ 端到端链路打通 |

> 复现命令：`.venv/bin/python scripts/parse_mineru_md.py data/parsed/moutai2024_fs`

#### ⚠️ 实测暴露的三个真实缺陷（必须写进方案，不能等踩到才知道）

1. **跨页表格不合并，且续页不重复表头。** 合并资产负债表横跨 p58–p61，被切成 4 个独立 `<table>`；表头 `项目 | 附注 | 2024年12月31日 | 2023年12月31日` **只出现在 p58**。p59 的第一行直接是 `拆出资金`，没有表头。
   → 后果：跨页拼接必须自己做，且必须**把首页表头向下传播**，否则续页数字没有列语义。
   → 影响组件：解析后处理模块。

2. **同一份文档内混用两种表格序列化。** p58–p60 输出 HTML `<table>`，p61 起切换为 markdown 管道表 `| 未分配利润 | 39 | ... |`。
   → 后果：解析器必须同时支持两种语法，否则会静默丢行。
   → 影响组件：解析后处理模块。

3. **本地解析服务会以 `BrokenProcessPool` 崩溃一次，之后自动重启即可成功。** 首次 `--tier standard` 解析失败，`~/.mineru/logs/doclib.stderr.log` 记录子进程 `Fatal Python error: init_sys_streams ... OSError: [Errno 9] Bad file descriptor`；服务随后打印 `Managed parse-server is unhealthy, attempting restart` 并自愈，**重试同一命令即成功**（第二次 39 秒完成）。
   → 处置：解析脚本必须内置"失败后重试一次"；不要把它误判为配置错误去反复改配置。
   → 根因：docvortex 的 PDF 渲染走 `ProcessPoolExecutor`（默认 3 进程，可用环境变量 `DOCVORTEX_PDF_RENDER_THREADS` / `MINERU_PDF_RENDER_THREADS` 调整），子进程继承了守护进程的失效文件描述符。

#### 降级链

```
MinerU（主）
  └─ 装不上 / 解析失败 → Docling（Apache-2.0，纯 CPU，带页码 provenance）
       └─ 跨页表格拼接错误 → 财报页改用 pdfplumber 规则提取 + 按重复表头拼接
            └─ 全部失败 → PyMuPDF 纯文本 + 页码，放弃表格结构，评测时如实报告该降级
```

#### 协议

MinerU 采用 *MinerU Open Source License*（基于 Apache 2.0 **附加商业使用条款与署名义务**，2026-04 修订）。**不是**网上流传的 AGPL。校招非商用项目无碍，正式使用前须核对仓库内 `LICENSE.md` 原文。

#### 明确不选

- **PP-StructureV3**：精度领先，但官方测试依赖 GPU（V100/A100），**Mac MPS 不支持**，CPU 慢跑不现实。
- **pdfplumber 作主解析**：规则法，合并单元格补 `None`、跨页不自动拼接，需大量手写后处理。
- **Marker**：跨页表格不合并（除非付费调 LLM），且无 bbox。

### 3.2 索引与定位

**选型：MinerU doclib（SQLite + FTS5）+ 自建 metadata 层**

MinerU 4.0 自带本地文档库，底层 SQLite，自带全文检索。**直接复用**，不再自建一套页码映射。

自建的只有一件事：在 MinerU 输出的块上挂六元组所需的 metadata（公司 / 期间 / 指标 / 数值 / 单位 / 页码 / 原文片段）。

#### ✅ 实测结论：locator 形态与 doclib 存储（2026-09-19 实跑）

**locator 形态已验证，与设计预期一致：**

```
doc:5299f49/tier:standard/page:59
doc:5299f49/tier:standard/page:59/block:3     ← 块级定位（read 的 content_ranges.end 返回）
```

- 文档 id = `sha256` 的前 7 位（`short_id`），可由 `mineru search` 直接取到。
- `mineru read "<locator>"` 返回该页 markdown + `content_ranges`（给起止 locator）+ `next_request.locator`（给下一页 locator，可顺序续读）。
- 1-based 页码，与 PDF 页码一致，**原生满足约束 #2**。

**doclib 实际存储字段（读 `~/.mineru/doclib.db` 的 schema 得到）：**

| 表 | 关键列 | 说明 |
|---|---|---|
| `docs` | `sha256` `short_id` `page_count` `language` `title` `author` `is_image_based` `meta_tier` | 文档级 metadata |
| `parses` | `sha256` `tier` `page_range` `status` `via` `done_at` | 解析任务与档位 |
| `fts_contents` | `sha256` `tier` `text` `title` `author` | **FTS5 虚表**，页面全文 |
| `fts_filenames` | `file_id` `filename` `ext` | FTS5 虚表，文件名 |

> **关键确认：doclib 不存 bbox 坐标。** 三张表都没有任何 `bbox` / `x` / `y` / 坐标列。
> 这从数据层证实了前面「MinerU 负责读懂、PyMuPDF 负责指得准」的判断不是推测——**想做页码 + 坐标双来源，PyMuPDF 是必需的，不是可选的**。已装 PyMuPDF 1.28.2 备用。

#### 复用它还是自建索引——实测后的结论

**词法层：直接复用 doclib 的 FTS5，但查询侧必须自己 jieba 切词**（原因见 §3.3）。
**自建的仍只有 metadata 层**：把六元组字段挂到 `doc:{id}/tier:{t}/page:{p}` 上，存进我们自己的 SQLite，用 locator 做外键关联回 doclib。这样不重复造索引，也不动 MinerU 的缓存。

### 3.3 检索

**选型：SQLite FTS5（jieba 分词）+ numpy 向量检索 → RRF 融合（k=60）。不引入向量库。**

#### 候选对比

| 方案 | metadata 可追溯 | 混合检索 | 抽象透明度 | 依赖轻量 | 学习成本 | 生态 |
|---|---|---|---|---|---|---|
| **SQLite FTS5 + numpy 自写** | 5 | 5 | 5 | 5 | 4 | 3 |
| Chroma（嵌入式） | 4 | 4 | 4 | 5 | 5 | 4 |
| Qdrant（本地） | 5 | 5 | 4 | 3 | 3 | 4 |
| LanceDB | 4 | 4 | 3 | 3 | 3 | 3 |
| FAISS | 1 | 2 | 4 | 4 | 3 | 5 |

#### 为什么不用向量库

单份年报切块后只有 **1k–5k 个 chunk**。5k × 768 维的全量余弦相似度就是 numpy 一次矩阵乘，微秒级。引入 Chroma / Qdrant 的边际收益约等于零，反而多一层需要在面试里解释的黑盒。

> **面试角度**：这里更加分的是"我论证了不需要向量库"——它证明你清楚自己的数据规模，也讲得清每一层在做什么。而且向量检索是自己写的，说明懂算法而非调包。

#### ★ 一个会静默产生假阴性的检索陷阱（2026-09-19 实测，必读）

**现象**：直接拿中文词去查 MinerU 的 FTS5，会 0 命中，且**不报错**——最危险的那种失败。

实测数据（对同一份已解析的茅台年报）：

| 查询 | 裸串 `match('资产总计')` | jieba 切词后 `match('资产 AND 总计')` |
|---|---|---|
| `资产总计` | **0（假阴性）** | **1 ✅** |
| `负债合计` | **0（假阴性）** | **1 ✅** |
| `货币资金` | 1 | 1（无回归） |

**根因（读 doclib schema 后确定）**：

1. `fts_contents` 建表语句是 `tokenize='unicode61'` —— 单看这句会误以为中文效果差。
2. 但**存进去的 `text` 已经被 MinerU 预先分好词了**，词与词之间用 ASCII `\x1f`（Unit Separator）分隔，形如 `...<\x1ftd\x1f>\x1f货币资金\x1f<\x1ftd\x1f>...`。unicode61 只负责把 `\x1f` 切开，所以**索引实际是 jieba 粒度的**。
3. 陷阱出在**查询侧**：`match('资产总计')` 的字符串会被 unicode61 当成**一个整词**去匹配，而索引里只有 `资产` 和 `总计` 两个词 → 必然 0 命中。

**实测交叉验证（这是关键）**：把 doclib 里 `\x1f` 切出来的词与 jieba 对同一原文的切词做集合比对——
**重合 445 个，MinerU 独有 0 个，jieba 独有 1 个（`年度报告`）**。
→ 结论：MinerU 内置 doclib 用的就是 jieba，**我们选 jieba 与它天然对齐，不需要换分词器，也不需要重建索引**。

**因此检索层的强制约定（已写入工程规范）**：

> 查询进 FTS5 之前**必须先用 jieba 切词、再用 ` AND ` 拼接**。
> 即 `match(" AND ".join(jieba.lcut(q)))`，不得把用户原串直接丢给 `match()`。
> 不做这一步 → 所有多字中文词检索返回空 → 被上层误判为"报告里没有这个数" → 直接导致本不该发生的**程序级拒答**。

> **面试角度**：这是一个"召回率假阴性"而非"精度"问题，而且是静默的。能讲清"索引侧分词粒度必须与查询侧一致"这件事，比背 FTS5 语法有说服力得多。

#### 两个必须做对的细节

1. **必须有确定性前置归一化。**（见下条）

2. **★ 数字归一化是检索成败的关键。** embedding 会把 `12,345.67`、`12345.67`、`1.23亿元` 当成三个互不相关的词串，因此**纯向量检索找财务数字必然失败**。必须先做确定性归一化：全角转半角 → 去千分位 → 数值与单位分离 → 统一换算到「元」。归一化文本进 BM25 索引，原值单独存列用于精确比较。

   这一层已实现并通过测试（`verifin/normalize.py`）。

#### 精排

可选 `bge-reranker-v2-m3` 对 top-20 精排 top-5。MVP 阶段先不接，留作 P1 阶段"核心优化"的消融项——这样消融实验才有东西可比。

#### RAG 编排框架

**不引入。** 本项目的核心难点是数字精确匹配、六元组校验、span 校验，**这三件事任何 RAG 框架都不解决**，必须自己写。引入框架只会在外面套一层需要解释的壳。

> 如果简历上需要一个框架名：只取 LlamaIndex 的 `BM25Retriever` + `QueryFusionRetriever` 两个组件，不用它的 Agent / Index 抽象。已知代价：内置 300+ 集成包，依赖树重。

### 3.4 Agent 编排

**选型：Pydantic AI 显式图 + LLM 经 function calling 自主选择工具**

#### 这一层是 Agent 定位的关键

「这算不算 Agent」取决于**谁在决定下一步**，不取决于用不用框架。为了让它经得起追问，做了两处设计：

1. **编排用显式图**，把 agent loop 画出来，循环与分支可视化、可复盘。
2. **工具调用不写死顺序**，由 LLM 通过 function calling 自主决定调哪个、调几次。

#### 候选对比

| 候选 | 图控制 | 黑盒度(低=好) | 结构化输出 | 可观测 | 模型无关 | 学习成本 |
|---|---|---|---|---|---|---|
| **Pydantic AI** | ★★★★ | ★★★★ | ★★★★★ | Logfire ★★★★ | ★★★★★ | 中 |
| LangGraph | ★★★★★ | ★★★ | ★★★★ | LangSmith ★★★★ | ★★★★★ | 重 |
| OpenAI Agents SDK | ★★ | ★★★★ | ★★★ | 需 key ★★★ | LiteLLM ★★★★★ | 低 |
| Microsoft Agent Framework | ★★★★★ | ★★★★ | ★★★★ | OTel ★★★★★ | ★★★★★ | 重（偏 Azure） |
| CrewAI | ★★★ | ★★ | ★★★ | ★★★ | ★★★★ | 中 |

#### 为什么是 Pydantic AI

- **`output_type` 强制 schema**：六元组字段约束能直接写成类型，与约束 #3 天然契合。
- **模型无关**：支持自定义 `base_url` + 任意模型名，当前这个中转端点可直接接入（已实测该端点不校验模型白名单）。
- **依赖 Pydantic**，与已实现的数据模型层同一套类型系统，不引入第二套建模方式。
- 相比 LangGraph 抽象更薄，面试时每一层都能讲清楚。

#### 为什么不用 LangGraph

不是不能用，是**性价比不合适**：本项目只有 2–3 个分支，LangGraph 的抽象层（StateGraph / checkpointer / 众多概念）带来的是需要额外解释的复杂度。而它对"Agent 合法性"的加分，Pydantic AI 的显式图同样能给。

#### 为什么不用 CrewAI / AutoGen

角色扮演式编排，**结构化输出弱**，且难以证明"LLM 自选了工具"——容易被面试官判定为黑盒。

#### 工具集设计（6 个工具，由 LLM 自主选择）

| 工具 | 用途 | 错误码 |
|---|---|---|
| `search_evidence` | 混合检索年报证据 | `NO_RESULT` |
| `locate_table_row` | 在财务报表页精确定位表格行 | `TABLE_NOT_FOUND` |
| `verify_identity` | 勾稽核验（走 Decimal） | `MISSING_OPERAND` |
| `convert_unit` | 单位换算（万元 ⇄ 元） | `UNIT_UNKNOWN` |
| `fx_rate` | 汇率查询（读本地汇率表，**不进提示词**） | `RATE_NOT_FOUND` |
| `list_periods` | 探查文档覆盖的报告期 | `NO_DOC` |

**LLM 的自主空间**：决定先检索还是先探期间、决定换关键词重试、决定调不调 `verify_identity`、决定够不够回答还是拒答。

#### Agent 合法性的五条可检验判据

| # | 判据 | 落法 |
|---|---|---|
| 1 | ≥2 个工具由 LLM 经 function calling 自主选择 | 6 个工具，不写死顺序 |
| 2 | 下一步由工具返回决定（条件边） | 证据不足 → 改写重试；缺字段 → 拒答 |
| 3 | 预算内自主终止 | `max_steps` / 时间 / 成本三重预算 |
| 4 | 工具观察回灌下一轮上下文 | 检索结果进下一轮 messages |
| 5 | 拒答是状态机可达状态 | 六元组缺字段 → 程序级拒答分支 |

这套「六元组 + Decimal + 程序级拒答」的设计**天然满足全部五条**——Agent 想给出答案，就必须先检索、再校验六元组、不足则拒答。

### 3.5 LLM

**选型：主 `glm-5.3`（当前中转端点）。廉价档候选 `qwen3.7-plus` / `deepseek-v4-flash`。**

#### 实测结论（2026-09-19，用你提供的端点亲测）

| 能力 | 结果 | 证据 |
|---|---|---|
| 基础对话 | ✅ | 正常返回 |
| **工具调用（function calling）** | ✅ | 模型正确选择 `search_annual_report`，参数 `{"metric":"营业收入","period":"2023-12-31"}` |
| **结构化输出（`json_schema`）** | ✅ | 返回合法 JSON |
| **span 逐字回吐** | ✅ | 模型回吐的 `source_span` 与原文逐字一致 |

第四项最关键：**span 硬校验机制依赖模型能准确回吐原文片段，这一点已实测成立**，不是假设。

#### 该端点可选的模型（实测 `GET /v1/models`）

`glm-5.2` `glm-5.3`｜`qwen3.6-plus` `qwen3.7-plus` `qwen3.7-max` `qwen3.8-max`(含视觉)｜`deepseek-v4-flash` `deepseek-v4-pro`｜`kimi-k2.6` `kimi-k2.7-code` `kimi-k3`(含视觉)｜`minimax-m3`

**用途**：跑"便宜模型能不能替代主模型"的消融实验时，直接改 `LLM_MODEL` 环境变量即可，不必换 SDK。

#### ⚠️ 一个必须写进报告的风险

实测中发现：**该端点接受了 `json_schema` 的 `strict: true` 参数，但并不真正强制必填字段**——同一段输入、同一个模型，有时返回全部 7 个字段，有时只返回 5 个。

**因此「结构化输出」不能作为字段完整性的保障。** 这是约束 #3 必须由程序级护栏兜底而不是靠提示词或 schema 的直接理由。

#### 配置方式

凭证只从环境读取（`.env`，已被 `.gitignore` 排除，不入仓库、不入日志）：

```ini

LLM_API_KEY=sk-...
LLM_MODEL=glm-5.3
```

走 OpenAI 兼容协议，换厂商只需改这三行。已实测：MinerU 依赖把 `openai` SDK 从 3.16.1 降级到 2.54.0，**LLM 客户端功能不受影响**（工具调用与结构化输出重测均正常）。

## 七、环境陷阱与绕行方案

### 7.1 pip 无法解包 sdist（本环境必踩）

**现象**：安装任何 sdist（`.tar.gz`）包报
`PermissionError: EEXIST: mkdir '<TMPDIR>/pip-install-*/<pkg>_<hash>'`

**排查过程**：`pip install` / `pip download` / 更换 `TMPDIR` / `--no-cache-dir` 全部无效；普通 `mkdir`、`curl`、`tar` 均正常；纯 wheel 包安装正常。**问题精确定位在 pip 解包 sdist 的代码路径。**

**绕行方案（已验证）**：从 PyPI 取源码包直链 → `curl` 下载 → `tar` 手动解压 → 装 `setuptools` 后 `pip install --no-build-isolation <本地目录>`。

已封装为 `scripts/bootstrap_env.sh` 中的 `install_sdist` 函数，可复用于其他只发 sdist 的包。

### 7.2 MinerU 的三个开关（见 §3.1）

### 7.3 MinerU 本地解析服务首次会长 `BrokenProcessPool`（已实测）

**现象**：`mineru parse ... --tier standard` 首次执行报错，`~/.mineru/logs/doclib.stderr.log` 出现
`Fatal Python error: init_sys_streams ... OSError: [Errno 9] Bad file descriptor`，
doclib 日志随后打印 `Managed parse-server is unhealthy, attempting restart`。

**这不是配置错误。** 服务会自愈，**原命令重试一次即成功**（实测第二次 39 秒完成 10 页 standard 解析）。

**不要做的事**：反复 `config set` / `server stop-start` / 重装模型——那是在错误方向上消耗时间。

**处置**：解析脚本内置一次自动重试。若需要从根上规避，可调低 PDF 渲染并发（`MINERU_PDF_RENDER_THREADS=1`、`DOCVORTEX_PDF_RENDER_THREADS=1`）。

### 7.4 网络注意

- GitHub raw 大文件偶发 `HTTP2 framing layer` / `Empty reply`，加 `--http1.1` 重试即可
- 巨潮资讯网 PDF 走 `static.cninfo.com.cn`，`www.cninfo.com.cn` 是 API 域
