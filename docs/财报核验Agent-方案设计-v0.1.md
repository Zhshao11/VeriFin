## 0. 一句话定位

输入一个关于 A 股年报的自然语言问题，输出一个**每个数字都能点回 PDF 原文页码**的答案；找不到证据就拒答，绝不补全。

---

## 1. 总体设计方案

**核心判断：这个任务的工程难点不是"让 LLM 更聪明"，而是"让 LLM 无法撒谎"。**

因此架构形态不是"LLM 自主 Agent"，而是**一条受约束的固定流水线**，只在两个位置把判断权交给 LLM（① 问题解析 ② 证据充分性初判），其余全部走确定性代码。这也符合你自己那份开发要求里的原则：固定工作流够用就先实现固定工作流，不强行包装成自主 Agent。

执行链路：

```
用户问题
  │
  ├─[1] 问题解析 (LLM)  → 任务类型 + N 个「检索单元」(指标 × 期间)
  │
  ├─[2] 混合检索        → BM25 + 向量 → RRF 融合 → 带页码/bbox 的 chunk
  │
  ├─[3] 充分性判定      → 每个检索单元都有满足约束的证据吗？
  │        │否 → 改写查询重试 (≤2 轮) ──┐
  │        │        │仍否 → 拒答        │
  │        └────────┴───────────────────┘
  │                │是
  ├─[4] 证据抽取 (LLM)  → 六元组 + 原文 span
  │
  ├─[5] Span 硬校验     → span 必须能在 chunk 原文里精确匹配，否则该证据作废 ★防幻觉核心
  │
  ├─[6] 计算 (纯代码)   → Decimal + 公式注册表，LLM 只选公式、不算数
  │
  └─[7] 答案组装        → 结论 + 六元组引用 + 可点击页码锚点
```

**三条不可越过的红线：**

| # | 红线 | 实现方式 |
|---|---|---|
| 1 | LLM 不产生任何数字 | 所有数值来自 span 校验通过的原文文本 |
| 2 | LLM 不做任何算术 | 算术全部走 `decimal.Decimal` + 公式注册表 |
| 3 | LLM 无权决定"猜一下" | 六元组缺任一字段 = 程序级拒答，模型没有否决权 |

## 2. 技术栈推荐

### 2.1 PDF 解析

| 候选 | 表格 | 跨页 | 页码定位 | 中文 | 部署 | 稳定 | 加权分 |
|---|---|---|---|---|---|---|---|
| **MinerU 4.0** | 5 | 3 | 4 | 5 | 3 | 3 | **4.05** |
| PP-StructureV3 | 5 | 3 | 4 | 5 | 2 | 3 | 3.95 |
| Docling (IBM) | 4 | 3 | 4 | 3 | 5 | 4 | 3.80 |
| PyMuPDF / 4LLM | 3 | 2 | **5** | 3 | 5 | 5 | 3.75 |
| pdfplumber | 2 | 1 | **5** | 3 | 5 | 5 | 3.35 |
| Marker | 3 | 2 | 2 | 3 | 3 | 3 | 2.60 |
| Unstructured | 2 | 2 | 3 | 2 | 2 | 3 | 2.35 |

> 权重：表格 25% + 页码定位 25% + 跨页 15% + 中文 15% + 部署 10% + 稳定 10%。
> 理由：本项目的判分点是"证据可追溯"，所以「页码定位」和「表格能力」必须最高权重；部署成本只要求 Mac 单机能跑，故压低。

**✅ 推荐：MinerU（主解析层）+ PyMuPDF（定位层/兜底）**

为什么不选单一工具：

- MinerU 承担表格 + 结构 + 中文，输出每块带 `page_idx` 和归一化 bbox（0–1000）。
- 但它的 bbox 是**归一化坐标**，不能直接在 PDF 上画框；且跨页表格默认只保留首页 `page_idx`，页码连续性会断。
- PyMuPDF 给**绝对坐标 + 精确页码**，正好补上可追溯性这一环，且 MinerU 单页失败时能兜底。
- 这一对组合全程免费、全 CPU 可跑，对校招 MVP 性价比最高。

**⚠️ 两条我实测复核过的事实（网上有错误传言）：**

1. **License 不是 AGPL。** MinerU 当前协议是 *MinerU Open Source License*（基于 Apache 2.0 + 附加条款，含商业使用条款与署名义务），2026-04 刚修订过。校招非商用项目无碍，但**上线前请以仓库内 `LICENSE.md` 原文为准**。
2. **模型体积不是 8GB。** MinerU 4.0 按 tier 分层：`basic` 约 0.8GB（ONNX，CPU 可跑，最低 2GB 内存）；`standard`/`advanced` 约 2–3GB。macOS Apple Silicon 是**官方推荐的一等路径**（standard tier = PyTorch + llama.cpp，base 包已自带 torch extra），建议 16GB 内存。

**降级路径（三层）：**

| 触发条件 | 降级动作 |
|---|---|
| MinerU 依赖装不上 / 太慢 | 换 **Docling**（Apache-2.0，CPU，带页码 bbox） |
| 跨页表格拼接结果错误（表头重复、行错位） | 财务报表页改用 **pdfplumber** 规则提取 + 按重复表头拼接 |
| 全部解析方案失败 | **PyMuPDF** 纯文本 + 页码，放弃表格结构，评测时如实报告该降级 |

**⛔ 不选 PP-StructureV3 的原因**：精度确实顶，但测试依赖 GPU（V100/A100），Mac MPS 不支持，CPU 慢跑不现实。

### 2.2 检索（RAG）

**✅ 推荐：不引入向量库，自建薄检索层。**

| 方案 | metadata 可追溯 | 混合检索 | 抽象透明度 | 依赖轻量 | 学习成本 | 生态活跃 |
|---|---|---|---|---|---|---|
| **SQLite FTS5 + numpy 自写** | 5 | 5 | 5 | 5 | 4 | 3 |
| Chroma（嵌入式） | 4 | 4 | 4 | 5 | 5 | 4 |
| Qdrant（本地） | 5 | 5 | 4 | 3 | 3 | 4 |
| LanceDB | 4 | 4 | 3 | 3 | 3 | 3 |
| FAISS | 1 | 2 | 4 | 4 | 3 | 5 |

**为什么不用向量库**：单份年报切块后只有 1k–5k 个 chunk，5k × 768 维全量余弦 = numpy 一次矩阵乘，微秒级。引入 Chroma/Qdrant 的边际收益 ≈ 0，反而多一层需要解释的黑盒。

> **面试角度**：这里更得分的是"我论证了不需要向量库"——它证明你清楚自己的数据规模、讲得清每一层在干什么。而且向量检索是自己写的，说明懂算法而非调包。

**RAG 编排框架：推荐也不引入。**

| 框架 | 判断 |
|---|---|
| **不用框架，自建薄层** | ✅ **首选**。本项目的核心难点（数字精确匹配、六元组校验、span 校验）**任何框架都不解决**，必须自己写。框架只会在外面套一层需要解释的壳 |
| LlamaIndex | ⚪ 备选。如果简历上需要一个框架名：只用它的 `BM25Retriever` + `QueryFusionRetriever`（`mode="reciprocal_rerank"`）两个组件，不引入它的 Agent/Index 抽象。已知代价：内置 300+ 集成包，依赖树重，安装体积大 |
| Haystack 2.x | ⚪ 备选。DAG + `.draw()` 最透明，面试讲层最稳，但生态较小 |
| LangChain / LangGraph | ❌ 不选。过度封装，栈深 15–40 帧，简单 RAG 反而贵 2.7× token |
| RAGFlow | ❌ 不选。Docker 服务端形态，chunk 级 metadata 与溯源不便，单进程约束下过重 |

**检索链路的具体落地：**

1. **BM25**：SQLite FTS5。⚠️ **必须换分词器**——FTS5 默认 `unicode61` 切中文很差，"营业收入"会召回崩掉，需接 jieba 或 trigram 分词。
2. **向量**：`bge-small-zh` 或 `bge-m3` 嵌入，`scores = emb_q @ E.T` 取 top-k（自己写，可讲清）。
3. **融合**：**RRF（k=60）**。小规模下最稳、免训练、免调权重。
4. **精排**：可选 `bge-reranker-v2-m3` 对 top-20 精排 top-5。MVP 阶段先不接，留作 P1 的"核心优化"消融项。
5. **★ 数字归一化（胜负手）**：embedding 会把 `12,345.67` / `12345.67` / `1.23亿元` 当成三个无关词，纯向量检索找财务数字**必然失败**。必须前置归一化：全角转半角 → 去千分位 → 数值 + 单位分离 → 追加单位锚（`[CNY]` / `[PCT]` / `[UNIT]`）。**归一化文本进 BM25 索引，原值单独存列**用于精确比较。

### 2.3 Agent 编排

**✅ 推荐：手写状态机 + Pydantic，不引入 Agent 框架。**

| 候选 | 图控制 | 黑盒度(低=好) | 结构化输出 | 可观测 | 模型无关 | 学习成本 |
|---|---|---|---|---|---|---|
| **手写状态机 + Pydantic** | ★★★★★ | ★★★★★ | 原生 | 自己打点 ★★★★★ | ★★★★★ | 无 |
| Pydantic AI | ★★★★ | ★★★★ | ★★★★★ | Logfire ★★★★ | ★★★★★ | 中 |
| LangGraph | ★★★★★ | ★★★ | ★★★★ | LangSmith ★★★★ | ★★★★★ | 重 |
| OpenAI Agents SDK | ★★ | ★★★★ | ★★★ | 需 key ★★★ | LiteLLM ★★★★★ | 低 |
| CrewAI / AutoGen | — | — | — | — | — | 范式不匹配 |

**理由**：整条链路只有「解析 → 检索 → 充分性判定 → (计算 / 拒答)」两三个分支，外加一个带上限的重试循环。`dict` 状态 + `while` 循环 + Pydantic 校验，约 150 行就能写完。

> **面试角度**：这题的加分项是"我判断出固定流程用不着 Agent 框架，只在意图解析和证据充分性两处引入 LLM 做判断"——体现的是工程判断力（知道什么时候不用工具）、全程可解释（没有框架黑盒）、预算控制就是一个计数器。比"我用了 LangGraph"更能扛住追问。

**⚪ 如果想在简历上挂一个框架名**：选 **Pydantic AI**（`pydantic_graph` 显式图结构 + 原生 Pydantic 结构化输出 + Logfire 可观测 + 完全模型无关）。**不选** LangGraph。

## 4. 四个防幻觉机制（面试追问的弹药）

这一节是整个项目的技术含量所在，建议精读。

### 4.1 Span 硬校验 —— 把幻觉变成可检测的程序错误

LLM 抽取数值时，**必须同时返回它认为的原文片段 `evidence_span`**。程序执行：

```python
assert evidence_span in chunk.text   # 精确子串匹配，不是模糊匹配
```

不成立 → 该条证据直接作废，不进入后续任何环节。

> 这比"在 prompt 里反复叮嘱模型不要编造"强一个数量级：**它把"模型可能撒谎"这个不可验证的问题，转化成了"字符串在不在原文里"这个可判定的问题。** 这是本项目最值得讲的设计点。

### 4.2 计算层与语言层彻底解耦

LLM 的输出**不是数字，而是"指标名 → 取值来源"的映射 + 一个公式 id**。真正的算术在代码里：

```python
class Formula(Protocol):
    id: str
    def evaluate(self, operands: dict[str, Decimal]) -> Decimal | Violation: ...
```

LLM 只能"选公式"，不能"算结果"。所有操作数必须来自 span 校验通过的证据。

### 4.3 拒答是程序状态，不是模型的自由发挥

```
if any(field is None for field in six_tuple):
    return Refusal(reason="EVIDENCE_INCOMPLETE", missing=field)
```

模型没有"我觉得差不多"这个选项。拒答率和拒答原因一并记录进数据库，用于评测。

### 4.4 充分性判定是确定性的，不是问模型"够不够"

不是把证据丢给 LLM 问"这些够吗"（模型会倾向于说够），而是**程序化检查**：

```
对每个检索单元 (指标, 期间)：
    是否存在至少一条证据，其 metadata 的指标与期间同时满足约束？
    否 → 该单元未覆盖 → 改写查询重试
```

判定标准可枚举、可测试、可复现。

## 5. 五个核心勾稽公式

| # | 公式 | 类型 | 容差策略 |
|---|---|---|---|
| **F1** | 资产总计 = 负债合计 + 所有者权益合计 | 恒等式 | 见下方容差规则 |
| **F2** | 利润总额 − 所得税费用 = 净利润；净利润 − 少数股东损益 = 归母净利润 | 恒等式 | 同上 |
| **F3** | 经营 + 投资 + 筹资净额 + 汇率变动影响 = 现金及现金等价物净增加额<br>期末余额 = 期初余额 + 净增加额 | 恒等式 | 同上 |
| **F4** | 毛利率 = (营业收入 − 营业成本) / 营业收入 × 100% | 派生量 | ±0.01 个百分点 |
| **F5** | 跨币种换算一致性：同一数值的双币种披露应满足汇率关系 | 恒等式 | 汇率精度决定 |
| **F6** | YoY 变动幅度合理性：\|变动率\| > 阈值 或 符号翻转 → 告警 | **启发式** | 阈值可配 |

### ⚠️ 一个必须在面试里讲清楚的口径问题

你原要求把「YoY 变化合理范围」和「跨币种换算一致性」列为"勾稽核验"。严格说：

- **F1–F3、F5 是恒等式**，等号左边必须等于右边，容差极小，不平衡即为**错误**。
- **F6（YoY）不是恒等式，是启发式**：变动 300% 不一定是错的（可能是并购、重组）。它只能触发**告警（warning）**，不能判定为**错误（error）**。

**所以核验结果要分三级输出：`PASS` / `WARN` / `FAIL`，而不是二值的通过/不通过。** 这个区分本身就是一个能扛追问的设计点——面试官很可能会问"你怎么知道变动 300% 就是错的"。

### ★ 容差怎么定（很容易被问倒的细节）

报表数字是**四舍五入到披露单位**的。若报表以万元为单位，每个科目有 ±0.5 万元的舍入误差，F1 涉及 3 个科目，误差可累积到 ±1 万元。

> **容差 = 参与运算的科目数 × 0.5 × 报表单位**

不能拍脑袋写 `abs(a-b) < 0.01`——那样所有恒等式都会误报 FAIL。**容差必须由报表披露单位推导出来**，且要作为配置项写进代码、在报告里说明。

## 6. 公开评测方案

### 6.1 一个必须先解决的冲突 ⚠️

你的要求里同时有两条互相矛盾的内容：

| 你的要求 | 冲突点 |
|---|---|
| 场景 = **A 股**上市公司年报 | FinanceBench 是**美国公司英文 10-K**，无任何中国公司、无中文 |
| ❌ 不用**商业受限**数据集 | FinanceBench 是 **CC-BY-NC-4.0（NonCommercial 非商用）** |
| 要点 5 = 用 **FinanceBench 50 题** | 它**无法验证中文 A 股年报的解析能力** |

**FinanceBench 已核实的事实**：Patronus AI 发布（arXiv:2311.11944，2023-11），论文口径 **10,231 题**，但**公开可下载的只有 150 题**（HuggingFace `PatronusAI/financebench`）。字段含 `company` / `doc_name` / `question_type` / `answer` / `evidence[]`，其中 **`page_number` 嵌在 `evidence` 数组里**（不是顶层字段）。覆盖约 32 家美企。PDF 在 GitHub 仓库，体积数百 MB，**不要 commit 进 git**。

**"每组至少 3 题、共 50 题"的可行性我算过了**：`⌊50 / 3⌋ = 16` 组上限。150 道开放题里有 32 家公司、其中 **25 家 ≥ 3 题**，所以凑 16 组完全够用，**不需要邮件申请全量数据**。

### ✅ 我的建议：三轨，各司其职

| 轨道 | 数据集 | 题量 | License | 作用 |
|---|---|---|---|---|
| **A** | FinanceBench 开放集 | 50 题 / 16 组 | CC-BY-NC-4.0 | **公开可比基线**——唯一带 `page_number` 证据的公开财报 QA 集，正好对应六元组的"来源页码"，且能支撑消融实验 |
| **B** | 自建 A 股评测集 | 30 题 | 交易所公开披露，注明来源 | **贴主场景**——验证中文 PDF 解析、A 股报表结构、勾稽公式 |
| **C** | FinQA / TAT-QA 抽样 | 20 题 | **CC-BY 4.0（可商用）** | **法律零风险补充**——验证数值推理，绕开 NC 限制 |

**关于 License 风险的判断**：FinanceBench 的 CC-BY-NC 禁止商业使用，但你这是**校招作品集（非商业）**。我的建议是**可以用，但必须在 README 顶部显式声明**数据来源、License 名称和非商用性质。这是学术界的标准做法，也是负责任的做法。如果你希望彻底无法律灰区，就用轨道 C 替代轨道 A——代价是**失去公开可比基线**（FinQA/TAT-QA 是"给定表格+文本片段做推理"，不含 PDF 解析环节，测不到我们的解析能力）。

**这道题需要你来拍板，见第 7 节。**

### 6.2 抽样规则

**Track A（50 题）**：按 `question_type` 分层，按公司分组，每组 3–4 题：

| 层 | 题型 | 题量 | 对应能力 |
|---|---|---|---|
| L1 | 单值抽取 | ~15 | 精确检索 + 数字定位 |
| L2 | 勾稽 / 计算 | ~25 | 多证据聚合 + Decimal 计算 |
| L3 | 综合判断 | ~10 | 多陈述推理 |

优先选 10-K、覆盖不同 GICS 行业，避免集中在同行业。

**Track B（30 题）**：5–8 家沪深蓝筹真实年报，结构对齐 Track A，**额外含 10 道"本该拒答"题**。

**拒答题怎么设计**（业界参考 SQuAD 2.0 + FinanceQA 2025 的做法）：
1. 问年报里**根本不存在**的指标（扰动题）
2. 需要跨年报对比、但**只给其中一份**
3. 缺少关键假设的"若…则…"问题

### 6.3 指标定义（必须写清分子分母）

| 指标 | 定义 |
|---|---|
| **单值核验准确率** | 数值在容差内 **且** 引用命中 gold 页码 的题数 / 该层题数 |
| **勾稽核验准确率** | 派生量值正确 **且** 公式步骤正确 的题数 / L2 题数 |
| **综合核验准确率** | 多陈述综合判断与 gold 一致 的题数 / L3 题数 |
| **拒答率** | 正确拒答数 / 不可答题总数（**单独报，不混入总分**） |
| **证据召回率** | 每题 top-k 命中 gold `page_number` 的证据数 / 标注证据数 |
| **引用支持度** | 抽查的「引用—结论」对中证据确实支持结论的比例（参考 RAGAS faithfulness） |
| **端到端耗时** | P50 / P95，注明失败任务口径 |
| **单次查询成本** | 所有 LLM 调用成本之和，注明模型与价格日期 |

### 6.4 消融实验设计

| 版本 | 配置 | 观察目标 |
|---|---|---|
| **V0 基线** | 纯向量检索 + LLM 直接回答 | 建立下界，观察幻觉率 |
| **V1 改进** | + 混合检索（BM25+向量+RRF）+ 数字归一化 | 检索增益 |
| **V2 完整** | + 六元组 + span 校验 + Decimal 计算（**证据可追溯**） | **核心消融点**：准确率↑多少？拒答率↑多少？ |

**V1 → V2 就是你要的那次消融实验**（基线 vs 加证据可追溯）。预期现象：准确率上升 **且拒答率显著上升**——这个"拒答率上升"不是缺点，恰恰是护栏在生效的证据，报告里要正面解释。

### 6.6 难度论证（可以引用的真实数字）

FinanceBench 原论文 Table 2：GPT-4-Turbo + 检索（共享库）**仅 19% 正确**；单文档向量库 50% 正确 / 39% 拒答；长上下文 GPT-4-Turbo 79%；**就算把正确页面直接喂给它（Oracle），天花板也只有 85%**——说明即便证据完美，仍有 15% 败在数值推理。论文口径 **66% 的题需要数值计算**。

## 7. 实施计划（6 天）

| 天 | 工作 | 验收 |
|---|---|---|
| D1 | 环境 + PDF 解析打通 + 数字归一化 + SQLite 建库 | 一份年报能解析出带页码的结构化 chunk |
| D2 | 检索层（FTS5+jieba / numpy 向量 / RRF）+ 六元组抽取 + span 校验 | 一个单值问题能带页码回答 |
| D3 | 状态机 + 计算层 + 5 个公式 + 工具契约 + 预算控制 + 异常处理 | 勾稽核验跑通；无证据能拒答 |
| D4 | 评测集构建（A/B/C 三轨）+ 跑 V0/V1 基线 | 拿到第一版真实失败案例 |
| D5 | V2 完整版 + 消融实验 + 指标汇总 | 完整结果表 |
| D6 | README + 失败案例记录 + 演示 + 简历条目 | 新环境能按 README 复现 |

> 你那份要求里强调"至少整理 3 个不同类型的实际问题"（输入/现象/原因/方案/验证/限制）。我的建议：D4 阶段故意记录 3 个——**跨页表格拼接失败**、**数字归一化漏匹配**、**拒答误触发**，这三个几乎必然会出现，且分别对应解析层、检索层、判定层，听起来最有说服力。
