> 本文件记录**设计层面 / 技术方案层面**出现过的问题及其解决方式。
> 目的：面试与复盘时能讲清「原来怎么做、为什么不行、后来怎么解决」。
> 最后更新：2026-09-19（已收录 P-001 ~ P-015）

## 零、收录规则（先读这条，避免本档被琐事稀释）

### 进档（满足任一）

| 类型 | 判据 | 说明 |
|---|---|---|
| A 方案短板 | 原技术方案或原设计假设**不成立**，必须**换方法**才能解决 | 例：以为解析器输出的定位信息够用，实测不够 |
| B 机制缺陷 | 存在会导致**静默错误**的机制（不报错但结果错） | 最危险的一类，优先级最高 |
| C 口径缺陷 | 数值口径 / 容差 / 单位推导的前提错了 | 直接影响核验结论可信度 |

### 不进档

| 类型 | 判据 | 本文档已出现的实例 |
|---|---|---|
| D 依赖与安装 | 缺库、包安装失败、版本降级 | pip 无法解包 sdist；`openai` 被 MinerU 锁到 `<3` |
| E 配置缺失 | 默认值不符合预期、开关没打开 | MinerU `--pages` 默认只解析前 10 页；`parse_server.local.mode` 默认 `disabled` |
| F 运行环境 | 进程崩溃、fd 失效、网络抖动，且有确定的重试/绕行手段 | 首次 `--tier standard` 崩 `BrokenProcessPool`，重试一次即成功 |
| G 纯代码手误 | 写错表达式导致的 bug，修掉即完事 | `"万元".endswith("万")` 写成假，导致万元按元处理（差 1 万倍） |
| H 性能调优 | 耗时、token 成本 | 单次 10 页解析 39 秒 |

> **G 类的例外**：手误本身不留档，但**由它提炼出的设计约定要留档**。
> 例：上面那条万元 bug，本体不留档；它引出的约定「单位识别必须用精确字典匹配，
> 不得用后缀包含判断」已写入 `.workbuddy/memory/MEMORY.md` 的工程约定。

### 每条必填字段

`原方案` → `短板` → `现象与实测证据` → `影响组件与后果` → `解决方案` → `验证` → `残留限制`

**`残留限制` 不可省略。** 一条问题只写"已解决"是不完整的——必须写清解决到什么程度、
边界在哪，否则下一个人会以为它被彻底消灭了。

## P-001 跨页表格被切成多个独立表格，且续页不重复表头

| 项 | 内容 |
|---|---|
| 类型 | A 方案短板 + B 机制缺陷 |
| 状态 | ✅ 已解决 |
| 发现日期 | 2026-09-19 |
| 影响组件 | 解析后处理模块 → 直接决定六元组「指标」字段能否确定 |

### 原方案

直接使用 MinerU 的 markdown 产物：它以 `<!-- page N of M -->` 按页组织，
每页的表格输出成一个 `<table>`。原设计假设「一页的表格就是一张表」。

### 短板

这个假设对财务报表不成立。**财务报表从来不是按页组织的**：

- 合并资产负债表横跨 p58–p61，MinerU 输出成 **4 个互不相干的 `<table>`**；
- **只有 p58 带表头**（`项目 | 附注 | 2024年12月31日 | 2023年12月31日`），
  p59 的第一行直接是 `拆出资金`，**续页完全没有表头**。

### 实测证据

```
页数 143｜表格块 14｜逻辑表 5      ← 拼接前是 14 个块，拼接后是 5 张逻辑表
  表#0  p58-p61  行数 104  列数 4  [跨页拼接｜html/markdown]
  表#1  p61-p63  行数 85   列数 4  [跨页拼接｜html/markdown]
  表#2  p63-p65  行数 65   列数 4  [跨页拼接｜html/markdown]
  表#3  p65-p66  行数 44   列数 4  [跨页拼接｜html/markdown]
  表#4  p66-p67  行数 53   列数 4  [跨页拼接｜html]
```

### 影响（为什么必须解决，而不是"凑合能用"）

续页的数字**没有列语义**——不知道第 3 列是"本期"还是"上期"。
直接后果：六元组里的「指标」字段无从确定 →
被判定为"证据不足" → **程序级拒答本可以回答的问题（假拒答）**。
对一个以"缺证据就拒答"为设计目标的项目，假拒答会直接损害可信度。

### 解决方案

新增 `verifin/tables.py`，把按页的块重建成逻辑表。续接判定用**三条同时成立**的确定性规则：

1. 当前块的首行**不是**表头行；
2. 当前块页码 == 上一逻辑表的 `page_end + 1`（紧邻下一页）；
3. 当前块列数 == 上一逻辑表列数。

第 1 条是整个方案的关键——**「没有表头」恰恰就是续页的信号**。
这比按表名或摘要判断更可靠，而且不需要任何模型参与，符合本项目「不做语义推断」的约定。

拼接时把首页表头**向下传播**，并给每行打上 `from_continuation` 标记。
**每一行都保留其真实来源页码**（`MergedRow.page`）——这是六元组页码溯源的前提，
拼接后如果丢了页码，整条证据链就断了。

### 验证

- `tests/test_tables.py` 32 项用例（含 2 项对真实产物的回归）
- 真实产物：`资产总计` 定位到 **p59**、`负债合计` 定位到 **p60**、
  `所有者权益（或股东权益）合计` 定位到 **p61**，与 PDF 实际页码一致
- 拼接后会计恒等式仍 PASS，差额 **0.00**（容差 ±1.5 元）——
  证明拼接没有把数字弄错位

### 残留限制

1. **当两张不同报表在相邻页且列数相同时，会被误合并。** 当前靠"出现表头即新表"来切分，
   若第二张表恰好没有表头行就会出错。已用 `flags` 字段对"未能续接"的情况告警，
   但反向（误合并）**目前没有自动检出手段**。
2. **列数取众数**（而非最大值）。遇到大面积错位页时众数可能不代表性。
3. 尚未处理**横向跨页**（列被切到下一页）的表格。

## P-002 同一份文档内混用两种表格序列化

| 项 | 内容 |
|---|---|
| 类型 | B 机制缺陷 |
| 状态 | ✅ 已解决 |
| 发现日期 | 2026-09-19 |
| 影响组件 | 解析后处理模块 |

### 原方案

解析器按 HTML `<table>` 语法提取表格。

### 短板

MinerU 在**同一份文档、同一张逻辑表内**会切换序列化方式：

- p58–p60 输出 HTML `<table><tbody><tr><td>`；
- p61 起输出 markdown 管道表 `| 未分配利润 | 39 | ... |`。

只支持一种语法 → **静默丢行**，且不报错。

### 实测证据

拼接结果中 `表#0` 的序列化字段为 `html/markdown` —— 两种都出现了。
若不处理，p61 上的 `未分配利润`、`所有者权益合计`、`负债和所有者权益总计`
**三行会全部消失**，恒等式将因缺科目而无法核验。

### 影响

静默丢行 → 科目缺失 → 假拒答；更糟的情况是关键的合计行丢失但上游没察觉。

### 解决方案

`verifin/tables.py` 定义 `Block` 作为统一内部结构，`_parse_html_table` 与
`_parse_markdown_table` 分别把两种语法解析成同一个 `Block`，
并按**出现位置**排序，保证与原文顺序一致。

### 验证

`test_parse_mixed_serialization_in_one_document` 与
`test_real_balance_sheet_is_stitched_across_four_pages`
（后者断言 `serializations == {"html", "markdown"}`）。

### 残留限制

目前只覆盖 MinerU 实际出现的这两种。若将来接入其他解析器（降级链上的 Docling /
pdfplumber）产出别的表示法，需要新增对应的 `_parse_*` 分支。

## P-003 FTS5 中文检索静默返回 0 命中（查询侧与索引侧分词粒度不一致）

| 项 | 内容 |
|---|---|
| 类型 | **B 机制缺陷（静默）** |
| 状态 | ✅ 已定位并定下强制约定；代码尚未落地 |
| 发现日期 | 2026-09-19 |
| 影响组件 | 检索层 |

### 原方案

复用 MinerU doclib 自带的 FTS5 全文检索，把用户查询串直接交给 `match()`。

### 短板

`match('资产总计')` 返回 **0 且不报错**。上层拿到空结果，
会判定为"报告里没有这个数" → **触发本不该发生的程序级拒答**。
这是召回侧的假阴性，比精度问题更隐蔽。

### 实测证据

| 查询 | 裸串 `match(q)` | jieba 切词后 `match(" AND ".join(...))` |
|---|---|---|
| `资产总计` | **0（假阴性）** | **1** |
| `负债合计` | **0（假阴性）** | **1** |
| `货币资金` | 1 | 1（无回归） |

**根因**（读 doclib schema 后确定）：

1. `fts_contents` 建表语句是 `tokenize='unicode61'`；
2. 但存进去的 `text` **已被 MinerU 预先分好词**，词间用 ASCII `\x1f`（Unit Separator）分隔，
   形如 `...<\x1ftd\x1f>\x1f货币资金\x1f<\x1ftd\x1f>...`。
   unicode61 只负责把 `\x1f` 切开，所以**索引实际是 jieba 粒度的**；
3. 陷阱在**查询侧**：`match('资产总计')` 的字符串被 unicode61 当成**一个整词**，
   而索引里只有 `资产` 和 `总计` → 必然 0 命中。

### 交叉验证（这条决定了我们不必重建索引）

把 doclib 里 `\x1f` 切出的词，与 jieba 对同一原文切词做集合比对：

```
重合 445 个    MinerU 独有 0 个    jieba 独有 1 个（「年度报告」）
```

→ **MinerU 内置 doclib 用的就是 jieba。** 我们选 jieba 与它天然对齐，
**不需要换分词器，也不需要重建索引，只需修查询侧。**

### 影响

若不修：所有多字中文词检索返回空 → 假拒答 + 评测集上召回率虚低，
且因为不报错，排查成本极高。

### 解决方案（强制工程约定）

> 查询进 FTS5 之前**必须先用 jieba 切词、再用 ` AND ` 拼接**：
> `match(" AND ".join(jieba.lcut(q)))`，
> 不得把用户原始查询串直接交给 `match()`。

### 验证

上表三组对照（含 `货币资金` 的无回归验证），且已写入 `MEMORY.md` 工程约定。
待检索层落地时补单测守住。

### 残留限制

jieba 与 MinerU 的切词有极小差异（实测 1 个词，`年度报告`）。
凡查询词恰好落在差异点上，仍可能漏召回。
**当前处置**：一律走 `mineru search` CLI 做召回，CLI 自带与索引一致的查询侧切词；
自建索引时再补"切词失败回退到逐字 AND"的兜底。

## P-004 doclib 不存 bbox 坐标，无法做坐标级高亮

| 项 | 内容 |
|---|---|
| 类型 | A 方案短板 |
| 状态 | ✅ 已解决（方案已定并落地依赖） |
| 发现日期 | 2026-09-19 |
| 影响组件 | 证据展示层（原文高亮定位） |

### 原方案

原设计假设「MinerU 原生输出稳定 locator，页码与块号齐全，可直接满足页码溯源」，
并据此把 PyMuPDF 定位为"锦上添花的补充层"。

### 短板

两层问题：

1. **doclib 根本不存坐标。** 读 `~/.mineru/doclib.db` 的 schema，
   `docs` / `parses` / `fts_contents` / `fts_filenames` **没有任何 bbox / x / y 列**；
2. MinerU 输出的坐标是**归一化 0–1000**，**不能直接在 PDF 上画框**。

结论：**PyMuPDF 不是可选组件，是必需组件。** 原方案把定位层写成"补充"是判断错误。

### 实测证据

```
docs        sha256 short_id size_bytes file_type page_count language title author
            subject keywords is_image_based meta_tier error_code error_msg ...
parses      id sha256 tier page_range status priority locked_at error_code ...
fts_contents  sha256 tier text title author          ← FTS5 虚表，无坐标列
fts_filenames file_id filename ext                   ← FTS5 虚表，无坐标列
```

### 影响

不做高亮的话，六元组只剩"页码 + 原文片段"，无法在 PDF 上框出证据位置。
对面试演示与人工复核都是明显缺失。

### 解决方案

保留双解析层的分工，并明确写进选型文档：

> **MinerU 负责"读懂"，PyMuPDF 负责"指得准"。**
> MinerU 出表格结构与页/块 locator；PyMuPDF 出绝对坐标与精确页码，
> 并可在 MinerU 单页解析失败时兜底。

已装 PyMuPDF 1.28.2，代码待写。

### 验证

schema 读取结果如上（可复现：用 `sqlite3` 只读打开 `~/.mineru/doclib.db` 查 `pragma table_info`）。

### 残留限制

跨页表格的坐标高亮尚未解决——表格跨页时首行表头在物理上只存在于第一页，
续页的框选只能框数字本身，无法连带表头。这是**物理限制**，不是实现缺陷。

## P-005 勾稽容差不能硬编码，必须由报表披露单位推导

| 项 | 内容 |
|---|---|
| 类型 | C 口径缺陷 |
| 状态 | ✅ 已解决 |
| 发现日期 | 2026-09-19 |
| 影响组件 | 核验层（公式判定） |

### 原方案

早期设计里容差是一个常数（如 `0.01`），隐含假设"报表以元为单位、保留 2 位小数"。

### 短板

这个假设对 A 股年报不成立。报表可能以**万元**或**百万元**披露，
此时每个科目天然带有 ±0.5 个披露单位的舍入误差，误差会随参与科目数累积。
用 `0.01` 元做容差 → **把所有以万元披露的报表全判成 FAIL（假阳性）**。

### 实测证据

茅台 2024 年报表头明确声明 `单位:元 币种:人民币`，该声明被 MinerU 原样解析出来。
反例推算：若报表以万元披露、3 个科目参与，
真实容差应为 `3 × 0.5 × 10000 = 15000` 元，而非 `0.01`。

### 影响

假阳性会导致把所有正常报表判成勾稽失败，核验结论完全不可用。

### 解决方案

`verifin/formulas.py` 的 `derive_tolerance`：
**`容差 = 参与科目数 × 0.5 × 报表披露单位`**，单位由报表表头的 `单位:` 声明解析得到，
不得硬编码。已断言 `derive_tolerance(3, "万元")==15000`。

### 验证

`tests/test_formulas.py` 用例；真实年报恒等式核验 PASS（容差 ±1.5 元）。

### 残留限制

披露单位必须**被解析出来**才能推导。若表头的 `单位:` 声明缺失或解析失败，
当前会回退到按「元」处理（偏保守，可能产生假阳性）。
调用方需检查 `is_known_unit()` 并在评测报告中标注该口径假设。

## P-006 结构化输出 strict 模式不被端点强制执行，字段会静默丢失

| 项 | 内容 |
|---|---|
| 类型 | B 机制缺陷 |
| 状态 | ✅ 已解决（程序级兜底） |
| 发现日期 | 2026-09-19 |
| 影响组件 | 证据抽取层 → 六元组完整性 |

### 原方案

用 `json_schema` + `strict: true` 让模型端点保证返回结构完整，
拿到的 JSON 直接当六元组用。

### 短板

端点**接受** `strict: true` 但**不强制**必填字段。实测 7 个字段只返回 5 个，
缺失字段无任何报错。

### 实测证据

`scripts/measure_schema_reliability.py` 实测：字段数 7 → 5。

### 影响

字段静默缺失 → 若直接把缺字段的 JSON 当完整证据用，就会**输出缺少证据的结论**，
违背本项目最核心的"缺证据拒答"目标。把正确性寄托在模型端点上是不成立的。

### 解决方案

不依赖模型自律，改为**程序级护栏**：

- `verifin/normalize.py::find_missing_fields` 逐字段检查六元组完整性；
- 缺任一字段 → 触发**程序级拒答**，不再调用模型判断；
- `verifin/llm.py` 保留 `json_schema → json_object` 的降级路径与重试，
  但**降级不是兜底手段，程序级检查才是**。

### 验证

`test_normalize.py` 中 `find_missing_fields` 用例（含"数值 0 不算缺失"的边界）。

### 残留限制

程序级检查能保证"不输出缺证据的结论"，但**不能恢复**模型漏掉的字段——
漏字段的查询会走向拒答而非回答。若拒答率过高，需要在抽取层加
"按字段逐个补抽"的第二轮调用。

## P-007 原方案把「numpy 向量检索」建立在外部 embedding 之上，但所用端点没有 embedding 能力

| 项 | 内容 |
|---|---|
| 类型 | **A 方案短板** |
| 状态 | ✅ 已解决 |
| 发现日期 | 2026-09-19 |
| 影响组件 | 检索层 |

### 原方案

选型文档写的检索架构是「SQLite FTS5 + **numpy 向量** → RRF 融合」。
「numpy 向量」隐含一个未言明的前提：**能拿到 embedding**。

### 短板

这个前提不成立。实测本项目使用的中转端点：

```
GET  /v1/models      → 18 个模型，其中 embedding 类 0 个
POST /v1/embeddings  → glm-5.3 / bge-m3 / text-embedding-3-large 全部 404
                       （model_not_found: not supported by any configured account）
```

也就是说：**没有可用的向量化来源**。原方案在这一层是悬空的——
它能写出来，但跑不起来。

### 影响

若照原方案写，会在"检索层跑通"这一步直接卡死；若退化成"只用 FTS5 单路"，
则 RRF 融合与消融实验都失去意义（融合至少要两路），选型文档里
"我论证了不需要向量库"这段论述也会变成"我根本没做向量"。

### 解决方案

**不假装存在，把降级做成显式、可插拔、可验证的一层。**

1. 定义 `Embedder` 协议（`embed(texts) -> ndarray`，要求 L2 归一化），
   向量通道只依赖这个协议而不依赖任何具体模型。
2. 默认实现 `TfidfEmbedder`：纯 numpy 计算 TF-IDF 余弦，**零外部依赖、确定性、可单测**。
3. `index_meta` 表记录当前用的是哪种向量实现，**把"用的是什么"写在数据里而不是藏在代码里**。
4. 顺手把架构从三路扩到**四路**，因为缺了 embedding 之后需要更多互补信号：

| 通道 | 作用 |
|---|---|
| `label` | 科目名精确匹配（BM25 分不清完整匹配与子串匹配） |
| `lexical` | FTS5 + jieba 的字面召回 |
| `numeric` | 归一化后的 Decimal 精确比较（红线 #4 的要求） |
| `vector` | 软匹配（多词部分命中给分） |

将来拿到 embedding 端点，只需写一个实现 `Embedder` 的类塞进 `RetrievalIndex`，
**其余代码一行不用改**。

### 验证

- `tests/test_retrieval.py` 覆盖四路各自的行为与融合公式
- 真实年报端到端：4 类查询（自然语言 / 科目名 / 精确科目名 / 纯数字）首位全部命中正确

### 残留限制

1. **TF-IDF 不等于语义向量。** 它只捕捉词面重合，**不理解同义词**——
   「营收」与「营业收入」在它的向量空间里是无关的。这是它相对真实 embedding 的实质差距，
   不能把它当成 embedding 的等价物。若评测集里出现较多同义表述，需要补词典或换真 embedding。
2. 向量通道与词法通道存在信号重叠（都基于词面），融合增益比"词法 + 真语义"要小。
   **这需要在消融实验里如实报告**，不能包装成"实现了混合检索"就完事。
3. IDF 与词典绑定：换词典需重建索引。

## P-008 jieba 默认词典不认识会计科目，导致「营业收入」被拆成两个通用词

| 项 | 内容 |
|---|---|
| 类型 | **B 机制缺陷（静默降级）** |
| 状态 | ✅ 已解决 |
| 发现日期 | 2026-09-19 |
| 影响组件 | 检索层（分词与排序） |

### 原方案

直接使用 `jieba.lcut` 做分词。**P-003 只解决了「索引侧与查询侧必须同源切词」，
但没有解决「词典本身是否覆盖领域术语」**——两者缺一都会静默降级。

### 短板

jieba 默认词典面向通用文本。实测：

```
jieba.lcut('营业收入')       -> ['营业', '收入']
jieba.lcut('营业总收入')      -> ['营业', '总收入']
jieba.lcut('手续费及佣金收入')  -> ['手续费', '及', '佣金', '收入']
```

`营业` 与 `收入` 这两个通用词在财报里遍地都是，于是查询
`2024年营业收入是多少` 的实际首条结果是 **`加:营业外收入`**，
真正的 `营业收入` 反而排在其后。

### 影响

**取错一个科目就等于取错一个数。** 而且这条错误不会报错——
它拿到的仍是一个"真实存在于报告里的数字"，可以一路通过 span 校验进入六元组。
这是全项目最危险的一类错误形态。

### 解决方案

新增 `verifin/lexicon.py`：

1. **财务专用词典**（`FINANCIAL_TERMS`，约 140 条）：覆盖资产负债表、利润表、
   现金流量表的准则列示项目与常用分析指标，通过 `jieba.add_word(freq=100000)`
   注入，保证在最大概率路径上一定被切出来。
2. **科目名前缀/后缀清洗**（`clean_label`）：
   - 序号前缀 `一、营业总收入` → `营业总收入`
   - 归属标记 `其中:营业收入` / `加:营业外收入` → 剥掉
   - 披露脚注 `净利润（净亏损以"-"号填列）` → `净利润`
   - **刻意不动** `所有者权益（或股东权益）合计`——它的括号是名字的组成部分

### 验证

加词典后同一查询的首条结果变为 `营业收入`（p63，170,899,152,276.34）；
`营业总收入`、`净利润` 也均能整词匹配。`tests/test_retrieval.py` 覆盖。

### 残留限制

词典是**手工维护**的小而准词表，必然存在长尾覆盖不到的科目名。
未加词典的复合词仍会被拆散。
**当前判断**：这个项目里"猜错"的代价高于"漏召回"，因此不做自动挖掘。
若评测暴露出漏词，按实际失败案例逐条补词，而不是放宽匹配规则。

## P-009 报表「附注」列被当作数值列，产生「未分配利润 = 39」这类错误

| 项 | 内容 |
|---|---|
| 类型 | **B 机制缺陷（静默错误）** |
| 状态 | ✅ 已解决 |
| 发现日期 | 2026-09-19 |
| 影响组件 | 检索层（数值通道与 chunk 构建） |

### 原方案

从表格行取数值时，直接取第 1 列之后的所有非空单元格：`cells[1:]`。
隐含假设是"第 0 列是科目名，其余都是数值"。

### 短板

A 股报表普遍有一列「附注」编号，位置正好在第 1 列：

```
| 项目 | 附注 | 2024年12月31日 | 2023年12月31日 |
| 未分配利润 | 39 | 182,787,415,205.05 | 172,983,178,300.09 |
```

取 `cells[1:]` 会把 `39` 当成第一个数值。

### 影响

六元组里的「数值」可能是 `39` 而不是 `182,787,415,205.05`。
更糟的是**这个错误能通过 span 校验**——`39` 确实出现在原文里。
护栏拦不住它，因为它不是幻觉，而是取错了列。

### 解决方案

`_value_column_indices(header, width)`：**由表头推导哪些列是数值列**，
把「项目 / 附注 / 科目 / 行次 / 序号」判为非数值列；
表头缺失时退化为 `1..width-1` 并交由调用方处理。

### 验证

`test_build_chunks_excludes_note_number_column` 断言 `未分配利润` 的 values
不含 `39` 且首项为 `182,787,415,205.05`。

### 残留限制

依赖表头被正确识别。若某张表没有表头行（拼接模块会对其打 `flags` 告警），
则退化为旧的 `1..width-1` 行为，附注列会重新混入。
**处置**：无表头的逻辑表应在入库前被拦截，而不是静默降级（待 Agent 层接入时补）。

## P-010 长科目名在 PDF 里会折行，按行分组做匹配会漏掉整行

| 项 | 内容 |
|---|---|
| 类型 | **A 方案短板** |
| 状态 | ✅ 已解决 |
| 发现日期 | 2026-09-19 |
| 影响组件 | 坐标层（PyMuPDF 定位） |

### 原方案

用 PyMuPDF 的 `search_for()` 定位文本；失败时退回自写的词级匹配，
**按 (block, line) 分组**在单行内滑动拼接。

### 短板

两个问题叠加：

1. `search_for` **不容忍 PDF 因字距插入的空白**：
   实测 `searchFor('59, 295, 822, 956.89')` 返回 0 处，而该数字在页上是存在的。
2. **长科目名会被折到下一行**。实测 `所有者权益（或股东权益）合计` 在第 61 页被切成
   `所有者权益（或股东权` + `益）合计`，分属相邻两行。
   按 line 分组意味着**跨行的标签永远拼不出来**，整行定位失败。

### 影响

六元组的「来源」字段拿不到坐标，证据无法在 PDF 上框出。
对这个项目而言，"指不出来"与"没有证据"在体验上是等价的——都会走向拒答。

### 解决方案

`_match_words` 改为**按 block 分组**（block 内按 `(line, x0)` 排序即阅读顺序），
**不再按 line 再切一层**，从而能把折行的标签重新拼起来。

新增伪命中防护：合并后矩形高度不得超过 `最大词高 × 2.6`（即最多跨 2 行）+
`MAX_LINES` 约束，避免窗口横跨不相干的表格行。

同时补上「只框真正构成匹配的那些词」：把窗口内每个词的字符区间记下来，
用 `acc.find(target)` 反查命中区间，**只合并与命中区间有重叠的词**。
（未做这一步时，框会把窗口起点之前的无关词一并框进去，
实测得到过 59.8 point 高的荒谬矩形——约等于 6 行。）

### 验证

8 个真实「科目 → 数值」用例全部通过同行校验；
`test_wrapped_label_is_located_across_two_lines` 守住折行场景。

### 残留限制

行数上限固定为 2 行。若某份报告把科目名折成 3 行，仍会漏。
放宽上限会同时放大伪命中风险，因此选择"漏"而不是"错"。

## P-011 坐标去重只比较 x 不比较 y，会把上下相邻两行的真目标吞掉

| 项 | 内容 |
|---|---|
| 类型 | **B 机制缺陷（静默错误）** |
| 状态 | ✅ 已解决 |
| 发现日期 | 2026-09-19 |
| 影响组件 | 坐标层 |

### 原方案

`_match_words` 命中后做去重，判据是
`abs(x0差) < 0.6 and abs(x1差) < 0.6` —— **只比了水平方向**。

### 短板

财务表格是分列对齐的：不同行的同一列，x 范围几乎完全相同。
于是**上下相邻两行的两处命中会被误判为"同一处的重复"，第二处被丢弃**。

实测触发：第 61 页上 `所有者权益（或股东权益）合计` 有两处候选：
- 一处嵌在 `归属于母公司所有者权益（或股东权益）合计` 里（y 92.8–117.1）
- 一处是它自己那一行（y 135.2–159.4）

两处的 x 范围几乎一致（95.7–221.8 vs 95.7–221.9），
于是第二处被去重吞掉，定位结果指到了**上面那一行**。

### 影响

坐标指错行 → 高亮框框在错误的行上 → 证据与数值不对应。
且因为 x 看起来"没错"，肉眼不易察觉。

### 解决方案

去重改为**四边都比**（`_nearly_same`：x0/x1/y0/y1 全在 0.6 容差内）。
同时在 `locate_row` 中把「在所有同行组合里挑垂直间隔最小的那一个」写成显式规则，
保证结果确定、可复现，而不是"取第一个碰巧对上的"。

### 验证

`test_substring_collision_prefers_the_row_containing_the_value` 断言
短标签与长标签必须落在**不同**的行上；
修复后 `所有者权益（或股东权益）合计` 的候选数由 1 变为 2（正确）。

### 残留限制

去重容差 0.6 point 是经验值。若页面存在极小的重复排版元素（如页眉的重复标记），
仍可能被视作不同命中而多返回一个候选；此时上层依赖同行校验来筛。

## P-012 公式注册表用规范科目名，报表用披露科目名，不一致会静默变成「缺操作数」

| 项 | 内容 |
|---|---|
| 类型 | **C 口径缺陷** |
| 状态 | ✅ 已解决（对齐表 + 只做精确命中与显式别名） |
| 发现日期 | 2026-09-19 |
| 影响组件 | 公式层 / Web 演示服务 |

### 原方案

`FORMULA_REGISTRY` 里 F1 的操作数写作
`('资产总计', '负债合计', '所有者权益合计')`，
调用方按这些名字去报表的行里取数，取不到就记入 `missing_operands`。

### 短板

报表披露的科目名与规范名并不是一套。茅台 2024 年报里那一行叫
**「所有者权益（或股东权益）合计」**，不是「所有者权益合计」。
按规范名取数 → 取不到 → 判定缺操作数 → 结论 `WARN`。

### 影响

`WARN` 的语义是「可疑但无法判定」，而这里的真实情况是「压根没取到科目」。
两者混成同一种结论，评测会把**对齐失败**误记成**数据可疑**，
核验报告也看不出该补的是一条别名。这是口径问题，不是取数代码的缺陷。

实测：补齐别名前 `/api/identity` 返回 `WARN / 差额 None`，
而三个操作数其实都在报表里（p59 / p60 / p61 都能取到）。

### 解决方案

1. 加**科目名对齐层** `LABEL_ALIAS`：规范科目名 → 该报表的实际行名，显式维护
2. 匹配只做**精确命中 + 显式别名**，**不做模糊包含** ——
   模糊包含会让「负债合计」落到「非流动负债合计」上，那正是本项目要防的张冠李戴
3. 仍然取不到时，返回的 `missing` 里给的是**规范名**，便于直接补进对齐表

### 验证

Web 演示服务 `/api/identity`：
对齐前 `WARN`，差额 `None`；
对齐后本期与上期均为 `PASS`，差额 `0.00`，容差 `1.5`（3 个科目 × 0.5 × 元）。

### 残留限制

对齐表目前是手填的。不同发行人的科目名差异更大（例如「母公司所有者权益合计」），
进入多公司评测前需要按**发行人维度**组织这张表，而不是一张全局表。

## P-013 选型承诺的「function calling 自主调工具」与红线 #1 正面冲突

| 项 | 内容 |
|---|---|
| 类型 | **A 方案短板** |
| 状态 | ✅ 已解决（换设计：LLM 只选节点，参数由图填） |
| 发现日期 | 2026-09-19 |
| 影响组件 | Agent 编排层（同时也是**框架选型的一次推翻**） |

### 原方案

`docs/技术选型-v1.1.md` §3.4 写的是
**「Pydantic AI 显式图 + LLM 经 function calling 自主选择工具」**，
并把「工具调用不写死顺序，由 LLM 自主决定调哪个、调几次」列为
「这算不算 Agent」的两条立身依据之一。

### 短板

function calling 的输入输出契约是：**模型产出工具名 + 参数**。
而本项目的六个工具里，`verify_span(claimed_value, claimed_fragment)` 的参数
就是这个待校验的数值本身。两处冲突：

1. **「LLM 不产生数字」这条红线被交出去了。**
   把 `claimed_value` 交给 LLM 填，等于让 LLM 产出数字；
   更麻烦的是，此时 span 校验变成「用 LLM 给的数值去校验 LLM 给的片段」——
   护栏仍在跑，但被护栏约束的两个量都由被约束方提供。
2. **span 校验不回答「这是不是你要的那个科目的数」。**
   它只回答「这个数字在不在原文里」。LLM 完全可以引用一段真实原文、
   报出该段里真实存在的另一个数字，校验**通过**，但取错了行。
   这个失败形态在本项目里**已经真实发生过两次**：
   P-008（排名被 `营业外收入` 抢走）与 P-009（取到「附注」列的 `39`）——
   两次都是「数字真实存在，但取错了科目」。

结论：**取数必须由程序按检索排名与表头推导来决定，不能由 LLM 报。**

### 影响

若不改：红线 #1 只剩下提示词层面的"请不要编数字"，
而这正是本项目用来区分「套壳 RAG」的那条线。整个项目最核心的
论证——「难点不是让 LLM 更聪明，而是让 LLM 无法撒谎」——会失效。

### 解决方案

**把 LLM 的权限从「调工具」收缩到「选节点」**：

- LLM 的返回值是一个受限枚举：当前节点的**合法后继里的一个节点名** + 一句理由；
- 工具入参一律由图从状态里填（`graph._fill_args`），LLM 看不到也没有机会写；
- LLM 选了合法后继之外的东西 → 丢弃，交给确定性兜底策略，并在轨迹里记 `raw_choice`；
- 这样 LLM 仍然**真的**在决定"下一步做什么"（不同证据状态下走不同的路），
  Agent 判据成立，但它碰不到任何一个数值。

同时**框架也换了**：不引入 Pydantic AI，Agent 层自写 4 个模块
（`graph.py` / `planner.py` / `tools.py` / `trace.py`，合计 1304 行）。
两条判据：

- Pydantic AI 的 `Agent` 是**工具自主循环**范式，它的图能力在**另一个库**（`pydantic_graph`）里；
  要用它做显式图就得同时接受两套抽象，而 `Agent` 的循环本身把控制流藏在内部 ——
  与「要能画出图、能对着一张节点表讲解」冲突；
- 核心链路必须**能在没有 LLM 的情况下跑通并被单测**，否则「LLM 不参与数值」无从验证。

替代方案的代价也如实记：`planner.py` 里那套合法后继校验、降级标记、
非法值纠正，如果框架自带就要自己写（约 60 行），判断是这个成本可以接受。

### 验证

- `tests/test_agent.py::test_tool_args_are_filled_from_state_not_llm` —— 用一个"在理由里
  塞假数字"的假调度器，断言该数字既没进任何工具入参，也没进最终答案；
- `test_llm_illegal_choice_is_corrected_by_graph` —— LLM 返回 `ANSWER`（不在合法后继内）时被纠正，且原样记下 `raw_choice`；
- `test_refusal_is_decided_by_program_not_by_planner` —— LLM 选 `ANSWER` 但六元组不全时，
  最终结果仍是程序级 `REFUSE`；
- 端到端：`scripts/demo_agent.py` 在 `--llm` 与无 LLM 两种模式下，
  同一问题的六元组与结论完全一致（仅 `decision.source` 字段不同）。

### 残留限制

1. **「框架选型被推翻」这一条是范式判断，不是实测否决。**
   本项目**没有安装过 Pydantic AI**（`import pydantic_ai` → `ModuleNotFoundError`，
   `pyproject.toml` 也未声明）。判据来自它的 API 契约与两条目标冲突，
   属于全项目里少数**没有实跑支撑**的取舍，面试时应如实说明，不要包装成"我试过不行"。
2. **LLM 的自主空间比原承诺小。** 原选型写的「决定换关键词重试」「决定先检索还是先探期间」，
   在当前图里只有"重走 SEARCH"这一条路（且兜底策略不走回头路，见 P-014）；
   工具集也从原计划的 6 个（含 `fx_rate` 汇率查询）换成了实际的 6 个
   （`search_statement` / `get_row_evidence` / `locate_in_pdf` / `verify_span` /
   `list_formulas` / `compute`）——`fx_rate` 因只做单份中文年报而砍掉，
   `convert_unit` 已被 `normalize.py` 覆盖。
   这是**自主性上的实际缩水**，不能因为"Agent 判据仍然成立"就不提。
3. **自写编排层没有生态。** 没有 Logfire/OTel 那类现成可观测性，
   `trace.py` 的 SQLite 轨迹是本项目唯一的可观测手段。

## P-014 确定性的兜底策略会原地打转，把「LLM 不可用」放大成「预算耗尽」

| 项 | 内容 |
|---|---|
| 类型 | **B 机制缺陷（且发生在兜底那一层）** |
| 状态 | ✅ 已解决 |
| 发现日期 | 2026-09-19 |
| 影响组件 | 调度层（`planner.policy_decide`）→ 直接决定 LLM 挂掉时还能不能答题 |

### 原方案

图里 `SEARCH` 的合法后继是 `("SEARCH", "EVIDENCE", "REFUSE")` ——
保留 `SEARCH` 是为了允许"换个关键词再搜一次"。
兜底策略 `policy_decide` 的做法是：按一张固定的节点顺序表
`SEARCH → EVIDENCE → VERIFY_SPAN → LOCATE → ANSWER` 推进，
**选第一个"在当前合法后继里"的节点**。

### 短板

顺序表的**第一项就是 SEARCH**，而 SEARCH 永远在自己的合法后继里。
于是兜底策略每一步都重新选中 SEARCH ——
图每走一步都消耗预算，`max_steps=12` 被同一个节点的自环吃光，最终落到 `ABORT`。

问题在于：**兜底层自己坏掉时，坏掉的方式和最需要它的场景重叠。**
LLM 不可用 → 走兜底 → 兜底自环 → 预算耗尽 →
一个本来完全能答的问题（证据在库里）被终止。

### 实测证据

第一次跑 `scripts/demo_agent.py --llm`，第二个问题返回 `ABORT` 而非答案。
轨迹里连续多步 `node=SEARCH`、`source=policy`，步数打满 12 才停止。
对照：单独跑同一个问题（LLM 正常）时为 `ANSWER`、5 步。

### 影响

1. **可用性被放大性损害**：LLM 抖动本应只降低"规划质量"，实际变成"整题不可答"。
2. **归因污染**：`ABORT` 的语义是"没算完"，与 `REFUSE` 的语义"证据不足"混在一起。
   评测时会把**规划器的缺陷**统计成**召回失败**，
   进而得出"检索层不行"的错误结论 —— 而检索层那一题其实是命中的。

### 解决方案

`policy_decide` 加两条写死的规则：

1. **不走回头路**：从顺序表里**跳过 `visited` 里已有的节点**。
   图里保留回边（给 LLM 用），但兜底策略不主动走回边。
2. **只有真的还有下一条候选时才重试**：上一步致命失败且 `has_more_candidates` 为真，
   才回到 `EVIDENCE` 换候选；否则直接 `REFUSE`，而不是继续在环里烧预算。

同时把 `ABORT` 与 `REFUSE` 在 `RunResult.decision` 里**保持区分**，
评测分开统计，避免上面第 2 类污染。

### 验证

`tests/test_agent.py`：
- `test_policy_skips_visited_nodes_to_avoid_self_loop` —— 直接断言
  `visited` 含 SEARCH 时兜底策略必须选 EVIDENCE 而不是 SEARCH（本缺陷的回归守卫）；
- `test_policy_retries_evidence_only_when_more_candidates_exist` —— 有候选才重试，否则拒答；
- `test_policy_treats_no_pdf_as_non_fatal` —— `NO_PDF` 不致命，不该导致拒答；
- `test_policy_is_deterministic` —— 同状态同结果；
- `test_step_budget_aborts` —— 预算确实耗尽时仍应 `ABORT`（守住"终止"这条路）；
- 端到端：`--llm` 模式下第二个问题恢复正常 `ANSWER`。

### 残留限制

**兜底策略不会真正重试 SEARCH。** "换关键词重搜"在 LLM 规划时会发生，
在兜底策略里不会发生。所以 LLM 全程不可用的场景下，
第一次检索没召回到就必然拒答。
这是**刻意选择**：宁可漏答，也不要因重试把预算烧光后给出语焉不详的 `ABORT`。
代价是「LLM 全挂时拒答率会偏高」，这个现象在消融实验里要能解释。

## P-015 LLM 调用预算被写成全局计数，第二次运行起静默降级为兜底策略

| 项 | 内容 |
|---|---|
| 类型 | **B 机制缺陷（静默降级）** |
| 状态 | ✅ 已解决（预算按运行重置 + Web 端调度器按请求隔离） |
| 发现日期 | 2026-09-19 |
| 影响组件 | 调度层（`LLMPlanner`）→ 直接污染消融实验的结论 |

### 原方案

`LLMPlanner` 自己持有 `self.calls`，`decide()` 里
`if self.calls >= self.max_calls` 就走兜底策略。
写的时候默认的前提是：**一个 planner 服务一个问题**。

### 短板

这个前提不成立。planner 是**被复用的**：

- Web 服务里是懒加载的**单例**（`web/server.py` 的 `_LLM_STATE`）；
- 演示脚本里一轮问多个问题，共用同一个 planner。

于是第一个问题把 8 次预算用完后，**之后每一个问题都直接走兜底策略**，
而且不报错、不告警 —— 只是"规划结果看起来朴素了一点"。

### 实测证据

顺序连问两题：第 2 题的轨迹里所有 step 的 `source` 全是 `policy`，LLM 调用计数为 0；
把第 2 题单独拿出来跑，`source` 是 `llm`。
唯一差异就是"前面问过一题"。

### 影响

这是评测里**最阴的一类污染**：V1/V2 消融会得出
「引入 LLM 调度没有带来提升」的结论，
而真实原因是第二个问题开始 LLM 根本没被调用。
`source="policy"` 这个标记一直都在（降级没有掩盖），
但当时没有人去读它 —— **有标记不等于会被发现问题**。
教训是：预算这类"会静默改变行为"的计数器，作用域必须写在代码结构里，
而不是靠"默认只服务一个问题"这种口头前提。

### 解决方案

把预算的所有权从 planner 移到**单次运行**：

- `VeriFinAgent.run()` 开头调用 `planner.reset()`；
- `Budget.max_llm_calls` 明确为 per-run 语义，与 `max_steps` / `max_tool_calls` 对齐
  （后两者本来就是 per-run，只有 LLM 计数漏了）。

### 验证

`test_llm_budget_is_per_run_not_global`：
构造一个"每一步都会被调用"的假客户端，连跑两个问题，
断言**两题都真实发生了 LLM 调用**（而不是只看第 2 题的结果对不对）。

### 残留限制

**并发的问题已在本轮修掉，但只保证逻辑正确，没有压测。**

原残留项是"Web 服务单进程共享一个 planner，并发请求互相偷预算"。本轮改法是：

- `web/server.py` 把「共享的 LLM 客户端」与「调度器」拆开 ——
  客户端共享（无状态、贵在建连），**调度器每请求新建**（`_fresh_planner`），预算按请求隔离；
- 顺手补了一处同源缺陷：`TraceStore` 此前只有 `check_same_thread=False`，
  但**"允许跨线程访问"不等于"跨线程安全"** —— 多请求同时 `execute` + `commit`
  会出现事务交错。已改为所有读写过一把 `threading.Lock`，
  并补 `test_trace_store_survives_concurrent_writes`（4 线程并发写 40 条，断言零异常、零丢记录）。

**仍然存在的限制**：没有做真实并发负载验证（只有单测级别的并发写），
所以"逻辑正确"是可证的，"高并发下性能与行为"未证。
不要因为这条被修过，就在评测报告里声称系统支持并发评测。
